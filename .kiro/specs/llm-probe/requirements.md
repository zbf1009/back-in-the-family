# Requirements Document

## Introduction

This is spec 3 of Back in the Family. `tech.md` still lists the LLM runtime as "Decided by the W1 probe". This spec builds that probe: a runner that sends the imported evaluation cards in `eval/cards/` to candidate runtimes and models, grades every answer with the rules from `eval/cards/README.md`, and measures quality, latency, cold start, download size and memory. The result is a written report, `docs/llm-probe.md`, with a recommendation per task type. The Author makes the final runtime decision from the report; this spec then records the decision in `tech.md` and `structure.md`.

The spec also builds two parts that later specs reuse:

- The **Output_Validator and Grader** in Rust, in `sim-core` (pure, deterministic, integer-only, no I/O), exposed to TypeScript through `sim-wasm`. The TS runner uses it now, and the browser game will use the same implementation for the LLM boundary in `tech.md` (parse, check option IDs, check referenced persons and events, check enums, fall back to the rules default).
- The **Runtime_Adapters** in TypeScript behind one interface, with a timeout and a fallback to the rules default: in-browser (WebLLM and transformers.js on WebGPU) and server (Cloudflare Workers AI, called in this probe through its REST API from the local runner; the game's server transport is decided in a later spec).

Two task types are measured, as defined in `eval/cards/README.md`: **D** (closed-set decision: pick one option ID from 2 to 5 options) and **S** (structured fact synthesis: return items in a fixed JSON schema with closed enums and event-ID evidence).

Author decisions already taken (not open for the design phase):

- B1: the Output_Validator and Grader are written in Rust in `sim-core` and exposed through `sim-wasm`; the TS side has no second implementation of the validation or grading rules.
- C3: in-browser runtimes are measured with Playwright on the system Chrome (`channel: 'chrome'`, no browser download) where WebGPU works headless; otherwise a dev-only Probe_Page is run by the Author in headed Chrome and exports results as JSON that the runner ingests.
- D1: for this probe (testing and debugging the runtimes), Workers AI is called through its REST API from the local runner. This spec deploys no Worker script, and keeping the site's hosting assets-only is a constraint of this spec only. D1 does not decide the production server-side inference path for the game (for example a deployed Worker that proxies Workers AI, with the request budget and rate limits from `tech.md`); that path is decided in a later spec.
- The card set is the one imported on 2026-11-06 and logged in `docs/kiro-log.md`. Its `MANIFEST.sha256` has the sha256 `9322729c727a8c975dc3273fb7cc2f239e8790ea66e1745493179aea6815b34f`.
- Decided 2026-11-06 after the design review: the proposed requirement changes RC-1 to RC-9 of `design.md` are applied below; the in-browser size option M is chosen (Requirement 9), on the principle that the Target_Machine is the upper bound of the hardware a demo visitor may have; the LFM Open License v1.0 of `LiquidAI/LFM2.5-1.2B-Instruct-ONNX` is accepted by the Author; and measurement follows a two-phase plan, browser first and server only where the browser fails (Requirement 18).
- Decided 2026-11-06 after Author review 1 of requirements and design: the once-only rule is keyed on the Model_Key, not on the Template_Hash or the sampling parameters (Requirement 3); the D answer format is one card-independent JSON object `{"option": string}` with no other member, and option-set membership is checked by the Output_Validator (Requirement 4); cold start, download and memory figures are measured at the start of each Locked_Run with a fresh browser profile (Requirement 14); a pass whose bootstrap lower bound is more than 10 percentage points under its Threshold is a pass with weak evidence (Requirement 13). Where the review offered alternatives, the first option was adopted.

- Decided 2026-11-09 after the Phase_1 and Phase_2 (branch B) Locked_Runs, where no Combination passed: the Author deferred the runtime decision and asked for an additional, separately approved Phase_2 candidate set of two Workers AI Decision_Models, `@cf/cloudflare/clef-flash` and `@cf/cloudflare/clef`, for Task_Type D only (Requirement 19). The same requirement adds the External_Reference ingest. Amendments to Requirements 4, 11, 12 and 18 are marked "Amendment (Requirement 19)" at the criterion they change.

Out of scope: wiring LLM results into the simulation's `TickInput` (no narrator nodes exist yet), the narrator, flavor text (dialogue, dreams, obituaries), deploying any Worker script or changing hosting, production rate limiting, a settings UI for the wait time, and editing any file under `eval/cards/`. The production server-side inference path (how the deployed game reaches Workers AI or another server model, for example through a Worker proxy) is also out of scope and left to a later spec; this spec neither rules it in nor rules it out.

### Open points for the design phase

These are deliberately not decided here:

- Q-open-1: which models to try per runtime (each in-browser candidate must meet the In_Browser_Size_Limits of Requirement 9), with their quantizations and licenses.
- Q-open-2: where the TS runner lives (under `eval/` as its own package, or inside `web/`), and how it shares the pinned pnpm, Type_Check and Unit_Tests setup.
- Q-open-3: how the Rust Output_Validator and Grader are exposed to Node (for example a second wasm-bindgen target, or loading the existing `--target web` output with `initSync` on the `.wasm` bytes), and whether the grading exports ship in the game's `sim-wasm` build or behind a feature.
- Q-open-4: how the Probe_Page is gated: a separate Vite entry or build that is not in the Deploy_Directory, or a dev-only entry inside it; and whether the Probe_Page needs cross-origin isolation (COOP/COEP, a `web/public/_headers` file) and what that does to the deployed site.
- Q-open-5: the exact answer format each prompt asks for (D: decided after Author review 1, the JSON object `{"option": string}` of Requirement 4 criterion 2; S: the family's JSON object), and whether the Output_Validator extracts one JSON value from surrounding text or requires the whole output to be JSON. Whatever rule is chosen is the same in the probe and in the game.
- Q-open-6: sampling parameters (temperature, top-p, maximum output tokens, seed where the runtime supports one), and whether any runtime uses constrained or grammar-guided decoding. Both are part of the Model_Fingerprint.
- Q-open-7: decided after Author review 1: the runner keeps a Late_Answer (Requirement 8 criterion 12) and reports "quality without timeout" figures next to the timed figures (Requirement 13 criterion 12).
- Q-open-8: the Request_Budget values (per-run cap, daily cap), the expected cost of a full locked run in Workers AI units, and the number of smoke calls that may run without asking. These are approved by the Author before the first Locked_Run.
- Q-open-9: the percentile method for latency (decided after Author review 1: nearest-rank with integer arithmetic, Requirement 14 criterion 1), the PRNG for the Cluster_Bootstrap, and the direction of "rotated by one" and "rotated by two" in the Shuffle_Test (the cards README does not fix the direction).
- Q-open-10: where the Locked_Run_Ledger and the Request_Budget counter are stored, and whether they are tracked in git.
- Q-open-11: how peak memory is measured for each runtime (for example browser process memory, WebGPU adapter limits), and what is reported where no measurement is possible.

Deferred to later specs (not for this design phase): the production server-side inference path for the game is undecided. A later spec decides how the deployed game reaches a server model (for example a Worker that proxies Workers AI) and how it applies the request budget and rate limits from `tech.md`.

## Glossary

- **Author**: the project owner. Approves pushes, deploys, global installs, remote resources, Workers AI spending beyond Smoke_Calls, the Request_Budget, and the final runtime decision.
- **Card_Set**: the directory `eval/cards/` exactly as imported, including `cards/dev.jsonl`, `cards/locked.jsonl`, `schemas/`, `MANIFEST.sha256` and `LOCK.md`.
- **Dev_Cards**: the cards in `eval/cards/cards/dev.jsonl` (34 cards).
- **Locked_Cards**: the cards in `eval/cards/cards/locked.jsonl` (108 cards).
- **Card**: one JSON line of the Card_Set, in the shape of `eval/cards/schemas/card.schema.json`.
- **Task_Type**: `decision` (D) or `synthesis` (S), the `task` field of a Card.
- **Scored_Card**: a Card with `scored: true`. Every non-sanity Card.
- **Sanity_Card**: a Card of family `sanity` (`scored: false`). Reported on its own, never in a Metric.
- **Void_Card**: a Card listed in the "Voided cards" table of `eval/cards/LOCK.md`. Excluded from every Metric.
- **Frozen_Context**: the `context` object of a Card (tick, subject, people, relations, events, situation, player input), plus the option list for D or the output schema name for S. The only input a prompt is rendered from.
- **Manifest**: `eval/cards/MANIFEST.sha256`, listing the sha256 of every other file in the Card_Set.
- **Pinned_Manifest_Hash**: `9322729c727a8c975dc3273fb7cc2f239e8790ea66e1745493179aea6815b34f`, the sha256 of the Manifest logged in `docs/kiro-log.md` on 2026-11-06.
- **Manifest_Check**: the check that the Manifest's own sha256 equals the Pinned_Manifest_Hash and that every file listed in the Manifest exists and has the listed sha256.
- **Output_Validator**: the Rust code in `sim-core` that decides whether one raw model output is legal for one Frozen_Context, and returns either a parsed answer or an illegal verdict with a reason.
- **Grader**: the Rust code in `sim-core` that assigns a Grade to a validated answer using the Card's answer key.
- **Grade**: for one answer, the three flags acceptable, severe and illegal, plus, for S, the list of severe conditions that fired.
- **Illegal**: an output that does not parse, names an option ID outside the Card's options (D), or fails the family output schema (S). Also any Timeout or runtime error, except the not-run and failure causes of Requirement 8 criterion 5.
- **Automatic_Severe**: the severe conditions `invented_event_id`, `invented_person` and `self_reference`, detected without patterns.
- **Pattern_Severe**: the severe conditions `reversed_direction`, `dead_person_as_actor_after_death`, `contradicts_fact` and `wrong_debt_holder`, detected through the Card's `severe_patterns`.
- **Pattern_Match**: the rule from the cards README: every field in the pattern matches; a scalar must be equal; a list means "equal to one of these"; `evidence_any` means the item's `evidence` contains at least one listed ID; in `relationship_shift_v1` the fields `a` and `b` are unordered.
- **Prompt_Renderer**: the code that renders a Frozen_Context, under one Permutation, into the prompt text sent to a model.
- **Prompt_Template**: the versioned text template used by the Prompt_Renderer, one per Task_Type or family.
- **Template_Hash**: the sha256 of a Prompt_Template's exact bytes.
- **Permutation**: for D, an ordering of a Card's options; for S, an ordering of the events within each block of events that share a tick. The base Permutation is the Card's own order.
- **Shuffle_Test**: the test from the cards README: each Scored_Card is run in its base Permutation and in the fixed Permutations reversed, rotated by one and rotated by two, with Permutations that equal the base or each other dropped.
- **Flip**: a non-base Permutation whose Identity_Value differs from the base run's.
- **Identity_Value**: for D, the chosen option ID; for S, the set of identity tuples per schema as listed in the cards README; the value `invalid` for an Illegal output.
- **Contrast_Pair**: two Cards with the same `pair_id`, roles `a` and `b`, differing in one stated fact.
- **Direction_Consistent**: a Contrast_Pair whose card-a base answer falls in `expected.a` and whose card-b base answer falls in `expected.b`, as defined in the cards README.
- **Runtime**: one inference engine: WebLLM (in-browser, WebGPU), transformers.js (in-browser, WebGPU), or Workers_AI.
- **Workers_AI**: Cloudflare Workers AI. In this probe it is called through its REST API from the local runner.
- **Combination**: one Runtime with one model and one set of sampling parameters.
- **Runtime_Adapter**: the TypeScript module that sends one prompt to one Runtime and returns the raw text, a Timeout, or an error, behind the Adapter_Interface.
- **Adapter_Interface**: the single TypeScript interface every Runtime_Adapter implements.
- **Timeout**: the per-request wait limit, 10,000 ms by default, configurable per run.
- **Generation_Cap**: for a request that hit the Timeout, the point at which the Runtime_Adapter interrupts generation: when the request's maximum output tokens are reached or Timeout + 60,000 ms after the request was handed to the Runtime, whichever comes first.
- **Idle_Cap**: Timeout + 90,000 ms after a timed-out request was handed to the Runtime; the latest time at which the Runtime_Adapter waits for the Runtime to stop generating that request.
- **Late_Answer**: the complete raw output text of a timed-out request that arrives after the Timeout and no later than the Generation_Cap. Kept for the "quality without timeout" figures only, never as the request's outcome.
- **Rules_Default**: the answer used when a model output is Illegal. In the game this is the rules-computed option; in the probe it is recorded as Illegal.
- **Probe_Runner**: the TypeScript program that loads the Card_Set, renders prompts, calls Runtime_Adapters, validates and grades outputs through Sim_Wasm, and writes Results.
- **Probe_Page**: the dev-only browser page that runs in-browser Runtime_Adapters in headed Chrome and exports results as JSON for the Probe_Runner.
- **Dev_Run**: a Probe_Runner run over Dev_Cards. Unlimited.
- **Locked_Run**: a Probe_Runner run over Locked_Cards for one Combination selected for the final measurement, restricted to one Task_Type_Subset.
- **Task_Type_Subset**: the non-empty set of Task_Types whose Scored_Cards a run covers: {D}, {S} or {D, S}. Sanity_Cards of the covered Task_Types are run with them.
- **Locked_Run_Ledger**: the persistent record of every Locked_Run started, with its Model_Key, Combination, Task_Type_Subset, Model_Fingerprint, start and end time and status.
- **Model_Key**: the identity of a model for the once-only rule of Requirement 3: the Runtime name, the model ID, the quantization and the Pinned_Revision (for Workers_AI, the value `server-side, not pinnable`). The Model_Key does not include the Template_Hash, the sampling parameters or the Combination's name.
- **Pinned_Revision**: the commit sha on the model host that an in-browser Combination's weight files, and for WebLLM its model library URL, are fetched from.
- **Warm_Up_Prompt**: one of two fixed prompts, one D-shaped and one S-shaped, not built from any Card, that an in-browser Runtime_Adapter runs after creating or rebuilding an engine.
- **Fresh_Profile**: a browser profile in a newly created temporary directory, holding no HTTP cache and no site storage, used for one Combination's performance measurement and deleted afterwards.
- **Exclusion_Record**: the record written when an in-browser candidate model is excluded by the In_Browser_Size_Limits screen, the pinning check or the VRAM_Preflight. A terminal Phase_1 state for that Combination.
- **Response_Shape**: the declared form of a Workers_AI model's REST response, recorded per model with the Combination (for example the chat shape, where the answer text is `choices[0].message.content`).
- **System_One_Shape**: the Response_Shape `system_one` of the Cloudflare System One API at REST `/ai/run/@cf/cloudflare/<model>`. The request body is `{model, state, questions}`. A `choice` question holds `instructions` and `criteria` (a map from option ID to description) and its answer is `answers.<question id>.choice`, with `confidence` and `probabilities`.
- **Decision_Model**: a Workers_AI model that follows the System_One_Shape and is measured for Task_Type D only: `@cf/cloudflare/clef-flash` (9B) or `@cf/cloudflare/clef` (27B).
- **System_One_Mapping**: the fixed mapping from a Frozen_Context and a Permutation to a System_One_Shape request: `state` is the rendered facts, one `choice` question holds `criteria` (option ID to label) and `instructions` (the content of the decision template's "How to read / How to choose" part).
- **Raw_Choice**: for a System_One_Shape response, the string `answers.<question id>.choice`. It is the raw output text of that request.
- **Truncated_State**: a request whose `state` the service cut to fit the Decision_Model's context window, or that cannot be shown not to have been cut.
- **Additional_Candidate_Set**: the Decision_Models `clef-flash` and `clef`, approved by the Author by name under Requirement 19.
- **External_Reference**: a measurement run outside this repository (for example a teacher model's locked upper bound) with its own frozen configuration and its own ledger. It is not a Combination, has no Locked_Run_Ledger entry here, and never counts toward a pass or fail mark or the Phase_2 branch logic.
- **External_Reference_File**: the file in which an External_Reference is handed over, with the hashes that Requirement 19 criterion 15 checks.
- **Approvals_File**: the file, at a path fixed in design, that records the Author's approvals of Workers_AI runs and of Phase_2.
- **Schema_Prefix**: the string `llm-probe-`, which starts the schema identifier carried by every record the Probe_Runner writes under `eval/results/` (for example `llm-probe-result-v1`).
- **Model_Fingerprint**: the record identifying what produced an output: Runtime name and version, model ID and Pinned_Revision or file hash, quantization, sampling parameters (with the seed recorded as `null` where the Runtime has no seed), the chat-template arguments passed to the model's chat template (for example `enable_thinking: false`), Template_Hash, the Pinned_Manifest_Hash, and for in-browser runs the browser version and the WebGPU adapter description.
- **Request_Budget**: the per-run cap and the daily cap on Workers_AI requests, plus the Neuron_Cap.
- **Neuron_Cap**: the daily cap of 9,000 estimated Workers AI neurons per UTC calendar day across all Workers_AI requests of the probe.
- **Smoke_Call**: a Workers_AI request made only to check connectivity or format, on Dev_Cards or a fixed test prompt, within a count fixed in design.
- **Workers_AI_Token**: the value of `WORKERS_AI_TOKEN` in the gitignored root file `env`.
- **Cloudflare_Account_ID**: the value of `CLOUDFLARE_ACCOUNT_ID` in the gitignored root file `env`, needed for the Workers AI REST URL.
- **Results**: the files the Probe_Runner writes under `eval/results/`.
- **Metric**: one of acceptable rate, severe count, illegal rate, Shuffle_Test flip rate, and contrast direction consistency, per Combination and Task_Type.
- **Threshold**: the pass value for a Metric from the cards README: acceptable rate at least 80%; severe count at most 1; flip rate at most 5%; contrast consistency at least 80% (D at least 12 of 15 pairs, S at least 8 of 10).
- **Random_Baseline**: the mean over scored D cards of |acceptable| / |options| (51.8% on the locked set).
- **Cluster_Bootstrap**: the confidence interval method from the cards README: resample whole scenario groups with replacement, 10,000 resamples, seed 20261104, report the 2.5th and 97.5th percentiles. Contrast consistency is resampled over pairs.
- **Wilson_Interval**: the unclustered Wilson 95% score interval.
- **Weak_Evidence_Margin**: 10 percentage points. A passing Metric whose bootstrap lower bound is more than this margin under its Threshold is a pass with weak evidence.
- **Report**: `docs/llm-probe.md`.
- **Target_Machine**: the Author's laptop: NVIDIA GeForce RTX 3050 Ti Laptop GPU with 4,096 MiB VRAM (driver 615.78.08), Intel UHD Graphics (TigerLake-H GT1), Intel i7-11800H (16 threads), 15 GiB RAM, Linux, Chrome 155. It is the upper bound of the hardware a demo visitor may have, not the typical case.
- **In_Browser_Size_Limits**: the size option M chosen by the Author on 2026-11-06, applied to the `q4f32_1` build (WebLLM) and the `q4` build (transformers.js): text-path download at most 1,536 MiB, at most 2.3 billion parameters (checkpoint total), and VRAM need at most 2,600 MiB (WebLLM `vram_required_MB`, or the VRAM_Preflight peak for transformers.js).
- **VRAM_Preflight**: for one transformers.js candidate model, loading the model on WebGPU on the Target_Machine and running one fixed test prompt that is not built from any Card, while recording peak VRAM with the method fixed in design. The prompt is at least max(8,000 bytes, 2 × the byte length of the longest rendered Dev_Card prompt) long and its synthetic context holds at least 8 events and at least 6 persons (Requirement 9 criterion 16), and the run generates 1,024 new tokens with the end-of-sequence stop disabled (only in the VRAM_Preflight).
- **Headless_Launch_Flags**: the fixed set of Chrome command-line flags, written in the design, with which headless system Chrome exposes the Target_Machine's hardware GPUs to WebGPU.
- **Software_Adapter**: a WebGPU adapter backed by a software or fallback renderer (for example SwiftShader) instead of a hardware GPU.
- **Phase_1**: the in-browser measurement phase of Requirement 18.
- **Phase_2**: the conditional server phase of Requirement 18, started only after the Author's go-ahead.
- **Sim_Wasm**: the wasm-bindgen output of `crates/sim-wasm`.
- **Gates_Script**: `scripts/gates.sh`.
- **Deploy_Directory**: `web/dist`, the only files deployed.
- **Size_Limit**: 26,214,400 bytes (25 MiB), the maximum size of any single deployed file.

## Requirements

### Requirement 1: Verify the Card_Set before any model run

**User Story:** As the Author, I want the runner to prove the cards are the ones I locked before it calls any model, so that no result can come from edited cards.

#### Acceptance Criteria

1. WHEN the Probe_Runner starts a Dev_Run or a Locked_Run, THE Probe_Runner SHALL run the Manifest_Check on that run's start, before reading any Card, rendering any prompt, writing any Results file, adding any Locked_Run_Ledger entry or sending any request to a Runtime, and SHALL NOT reuse the outcome of a Manifest_Check from an earlier run.
2. IF the sha256 of the Manifest differs from the Pinned_Manifest_Hash, THEN THE Probe_Runner SHALL print the expected and the actual hash, each as 64 lowercase hexadecimal characters, and SHALL exit with a non-zero status without sending any request, writing any Results file or adding any Locked_Run_Ledger entry.
3. IF one or more files listed in the Manifest are missing, unreadable, or have a sha256 different from the listed value, THEN THE Probe_Runner SHALL check every listed file before exiting, SHALL print the path of every mismatched, missing or unreadable file (not only the first), and SHALL exit with a non-zero status without sending any request, writing any Results file or adding any Locked_Run_Ledger entry.
4. THE Probe_Runner SHALL take the Pinned_Manifest_Hash from exactly one constant in source code, and the Manifest_Check run by the Gates_Script SHALL use that same constant, so that the 64-character hash value appears exactly once in the Probe_Runner and Gates_Script source and changing the accepted Card_Set requires a code change.
5. THE Probe_Runner SHALL open the files under `eval/cards/` for reading only, so that after any Dev_Run, Locked_Run or Manifest_Check, every file under `eval/cards/` has the same bytes as before, and no file under `eval/cards/` has been created, deleted or renamed.
6. WHEN the Gates_Script runs, THE Gates_Script SHALL run the Manifest_Check without making any network request and without reading the Workers_AI_Token, and SHALL fail with a non-zero status if the Manifest_Check fails, so that an edit to any file listed in the Manifest, or to the Manifest itself, fails the gates.
7. WHERE the Manifest_Check hashes files under `eval/cards/blind/`, `eval/cards/review/locked.md` or `eval/cards/cards/locked.jsonl`, THE Manifest_Check SHALL print only paths and hashes for those files, and no file content, on standard output, on standard error and in error messages, in both the pass and the fail case.
8. IF the Manifest is missing or unreadable, or any line of it is not a 64-character lowercase hexadecimal sha256 followed by a file path, THEN THE Probe_Runner SHALL print an error naming the Manifest and the line number of each malformed line, and SHALL exit with a non-zero status without sending any request, writing any Results file or adding any Locked_Run_Ledger entry.
9. IF a path listed in the Manifest is absolute or resolves outside `eval/cards/`, THEN THE Manifest_Check SHALL treat that entry as a failure, print the offending path, read no file at that path, and exit with a non-zero status.
10. WHEN the Manifest's sha256 equals the Pinned_Manifest_Hash and every listed file exists and matches its listed sha256, THE Probe_Runner SHALL print a single pass line that contains the Pinned_Manifest_Hash and the number of files checked (27 for the imported Card_Set), and SHALL then continue with the run.

### Requirement 2: Load Cards and respect Void_Cards

**User Story:** As the developer, I want cards parsed into typed values with the void list applied, so that every later step works on the same, checked data.

#### Acceptance Criteria

1. WHEN the Probe_Runner loads a split, THE Probe_Runner SHALL parse every non-empty line of the split's `.jsonl` file into one Card and SHALL check four counts against the "Contents" table of `eval/cards/LOCK.md`: total Cards (34 dev, 108 locked), Scored_Cards with Task_Type `decision` (18 dev, 60 locked), Scored_Cards with Task_Type `synthesis` (12 dev, 40 locked), and Sanity_Cards (4 dev, 8 locked).
2. IF any count from criterion 1 differs from the value recorded in `eval/cards/LOCK.md`, THEN THE Probe_Runner SHALL exit with a non-zero status before sending any request, SHALL print the split, the count name, the expected value and the actual value, and SHALL write no Results file for that run.
3. IF a line fails to parse as a Card, THEN THE Probe_Runner SHALL exit with a non-zero status before sending any request, SHALL print the 1-based line number, SHALL also print the Card ID when the line is valid JSON with a string `id` field, and SHALL write no Results file for that run.
4. IF two Cards in the Card_Set have the same Card ID, within one split or across the dev and locked splits, THEN THE Probe_Runner SHALL exit with a non-zero status before sending any request and SHALL print the duplicated Card ID and the line numbers of both occurrences.
5. WHEN the Probe_Runner loads the Card_Set, THE Probe_Runner SHALL read every data row of the "Voided cards" table of `eval/cards/LOCK.md` and SHALL mark the Card ID in each row's "Card" column as a Void_Card. A row whose "Date" cell is `none` and whose "Card" cell is empty means that no Card is void and SHALL produce zero Void_Cards.
6. IF the "Voided cards" table is missing from `eval/cards/LOCK.md`, or a data row other than the `none` row has an empty "Card" cell, THEN THE Probe_Runner SHALL exit with a non-zero status before sending any request and SHALL print an error identifying the missing table or the malformed row.
7. IF the "Voided cards" table names a Card ID that is not in the Card_Set, THEN THE Probe_Runner SHALL exit with a non-zero status before sending any request and SHALL print that Card ID.
8. THE Probe_Runner SHALL exclude Void_Cards and Sanity_Cards from every Metric, SHALL exclude a Contrast_Pair from contrast consistency when either Card of the pair is a Void_Card, and SHALL list in the Results every excluded Card ID and every excluded `pair_id`, each with its reason (`void` or `sanity`). The list SHALL be stored in the Results grades format as a field `excluded` holding a list of objects `{id, reason}`, where `id` is a Card ID or a `pair_id`.
9. THE Card parser SHALL accept only integer values for every numeric field, SHALL reject a Card that contains any non-integer number (for example `3.5` or `1e2`), and SHALL handle that rejection as a parse failure under criterion 3.
10. FOR ALL valid Cards, parsing a Card, serializing the parsed value to JSON, and parsing that JSON again SHALL produce a value equal to the first parsed value (round-trip property).

### Requirement 3: Keep the Locked_Cards blind and run them once

**User Story:** As the Author, I want prompt engineering to touch only the dev cards and each final combination to see the locked cards once, so that the locked score is an honest estimate.

#### Acceptance Criteria

1. THE Probe_Runner SHALL be the only program that reads `eval/cards/cards/locked.jsonl` for anything other than the Manifest_Check. Only a Locked_Run, including building a Probe_Page prompt bundle for a Locked_Run, SHALL render prompts from Locked_Cards. Ingesting a Probe_Page file, re-grading stored Results and building the Report SHALL be allowed to read `eval/cards/cards/locked.jsonl` for grading and statistics only, SHALL render no prompt from a Locked_Card, and SHALL emit no Card content other than Card IDs, `pair_id`s and scenario group IDs. Amendment (RC-13, 2026-11-09): ingesting an External_Reference_File (Requirement 19 criterion 15) SHALL be added to that list of readers, with the same limits.
2. WHILE a Dev_Run is in progress, THE Probe_Runner SHALL load Cards only from `eval/cards/cards/dev.jsonl`. No prompt sent during a Dev_Run SHALL be rendered from a Locked_Card's Frozen_Context.
3. WHEN a Locked_Run starts, THE Probe_Runner SHALL append an entry to the Locked_Run_Ledger before it sends the first request. The entry SHALL hold a unique entry ID, the Model_Key, the Combination, the Task_Type_Subset, the Model_Fingerprint, the Template_Hash of every Prompt_Template in use, the start time and the status `in progress`.
4. IF the Probe_Runner cannot write the Locked_Run_Ledger entry when a Locked_Run starts, THEN THE Probe_Runner SHALL send no request, report an error naming the ledger write failure, and exit with a non-zero status.
5. WHEN every Card and Permutation combination of a Locked_Run has a recorded output and no not-run Results record of that Locked_Run remains, THE Probe_Runner SHALL set that ledger entry's status to `complete` and record the end time. An entry with any remaining not-run record SHALL NOT be `complete`. Any entry whose status is not `complete` counts as incomplete, including an entry left behind when the process was killed.
6. IF a Locked_Run is requested for a Model_Key that already has a Locked_Run_Ledger entry, `complete` or incomplete, whose Task_Type_Subset shares at least one Task_Type with the requested Task_Type_Subset, and the request is neither a resume of that incomplete entry (criterion 9) nor a re-run with the re-run flag and a reason that is not empty or whitespace only, THEN THE Probe_Runner SHALL send no request, leave the Locked_Run_Ledger and Results unchanged, and exit with a non-zero status. Its error message SHALL name the existing entry ID. This SHALL hold whatever the Template_Hash, the sampling parameters or the Combination's name of the request. A request whose Task_Type_Subset shares no Task_Type with any entry of the same Model_Key is not a re-run.
7. WHEN a Locked_Run is re-run with the re-run flag and a non-empty reason, THE Probe_Runner SHALL record in the new Locked_Run_Ledger entry the reason and, as `rerun_of`, the ID of the earlier overlapping entry (`complete` or incomplete), and SHALL leave the earlier entry and its Results byte-for-byte unchanged.
8. WHEN two or more Locked_Run_Ledger entries exist for the same Model_Key with Task_Type_Subsets that share a Task_Type, THE Report SHALL list every one of those runs with its entry ID, status and Metrics. For each Model_Key and Task_Type, THE Report SHALL use only the first `complete` entry (the one with the earliest start time) for its pass or fail marks and recommendation, SHALL name that entry ID, and SHALL list later entries as re-runs that are not used.
9. WHEN an incomplete Locked_Run is resumed, THE Probe_Runner SHALL send requests only for the Card and Permutation combinations that have no recorded output. It SHALL keep every recorded output unchanged and continue the same ledger entry, and the resume SHALL NOT count as a re-run.
10. IF a resume is requested and the current Model_Key, Model_Fingerprint or any Template_Hash differs from the one recorded in the incomplete ledger entry, THEN THE Probe_Runner SHALL send no request, leave the ledger entry and Results unchanged, and exit with a non-zero status. Its error message SHALL say that a changed Template_Hash or sampling parameter for the same Model_Key requires a re-run with a reason (criterion 7), not a resume.
11. WHILE a Locked_Run is in progress, THE Probe_Runner SHALL write only progress counts, aggregate Metrics and error messages to standard output and standard error. Those streams SHALL contain no Card content other than Card IDs, no prompt text and no model output.
12. IF a Locked_Run starts and either no Dev_Run of the same Combination covering every Task_Type of the Locked_Run's Task_Type_Subset is recorded, or the Template_Hash of any Prompt_Template in use differs from the Template_Hash recorded by the most recent such Dev_Run, THEN THE Probe_Runner SHALL send no request, write no Locked_Run_Ledger entry, and exit with a non-zero status. Its error message SHALL name the missing Dev_Run or each mismatched Prompt_Template.
13. THE Deploy_Directory SHALL contain no file that includes any line of `eval/cards/cards/locked.jsonl`, and no file copied from the Results under `eval/results/`. THE Gates_Script SHALL check this without reading `eval/cards/cards/locked.jsonl`: it SHALL fail if any Deploy_Directory file contains the marker strings `"author_note"` or `"severe_patterns"` (present in every Card line) or the Schema_Prefix `llm-probe-` (present in every record under `eval/results/`), or if any file under `web/` imports from `eval/` (criterion 16). The game's Sim_Wasm build in the Deploy_Directory SHALL pass this check, so its error strings SHALL name answer-key fields without the quoted forms above.
14. WHILE a Dev_Run or Locked_Run with a Task_Type_Subset is in progress, THE Probe_Runner SHALL send requests only for Cards whose Task_Type is in that Task_Type_Subset.
15. WHEN a Locked_Run (or a Probe_Page prompt bundle for a Locked_Run) is requested, THE Probe_Runner SHALL render every Card and Permutation of the run before it writes the Locked_Run_Ledger start entry. IF any render returns an error under Requirement 7 criterion 9, THEN THE Probe_Runner SHALL send no request, write no Locked_Run_Ledger entry and no Results, print the Card ID and reason of every render error, and exit with a non-zero status.
16. THE Gates_Script SHALL fail, naming the importing file and the imported path, if any file under `web/` imports, re-exports or dynamically imports any path under `eval/`, including imports with a query suffix such as `?raw` or `?url`.

### Requirement 4: Output_Validator in `sim-core`

**User Story:** As the developer, I want one Rust validator that turns raw model text into a checked answer or a clear illegal verdict, so that the probe and the game reject the same outputs.

#### Acceptance Criteria

1. THE Output_Validator SHALL live in `sim-core`, use integers only (no `f32`/`f64` in its types or logic), perform no I/O, read no clock, read no environment and use no randomness.
2. WHEN given a raw output and a D Frozen_Context, THE Output_Validator SHALL return exactly the chosen option ID if the output parses under the answer format fixed in design as one JSON object with exactly one member, `option`, whose value is a string (the same card-independent schema for every D Card, with no other member allowed), and that string is equal, by exact string comparison, to one of the Frozen_Context's option IDs.
3. WHEN given a raw output and an S Frozen_Context, THE Output_Validator SHALL return the parsed items if the output parses and passes every check of the family output schema named by the Frozen_Context (`grudge_v1`, `debt_chain_v1`, `broken_promise_v1` or `relationship_shift_v1`): every required field is present; no field outside the schema is present, at the top level or in any item; every closed enum value is one the schema lists; every integer field holds a JSON number with no fraction part and no exponent part whose value lies in the signed 64-bit range and at or above any `minimum` the schema sets (for example `amount` at least 0); every event-ID field (`origin_event`, `promise_event`, `turning_point`) matches `^e[0-9]{1,4}$`; and `evidence` holds at least 1 string, with no duplicates, each matching `^e[0-9]{1,4}$`.
4. IF the raw output does not parse under the answer format fixed in design, THEN THE Output_Validator SHALL return an Illegal verdict with a reason code that identifies a parse failure.
5. IF a D raw output parses but names an option ID that is not one of the Frozen_Context's option IDs, THEN THE Output_Validator SHALL return an Illegal verdict with a reason code that identifies an out-of-set option ID.
6. IF an S raw output parses but fails a check listed in criterion 3, THEN THE Output_Validator SHALL return an Illegal verdict with a reason code that identifies the failed check and the field path where the first failure occurred. The reason codes SHALL be: missing required field; unknown field; value of the wrong JSON type (`wrong_type`, for example a string where an integer is required); wrong `schema` constant (`wrong_schema_const`); illegal enum value; non-integer value; out-of-range integer (`integer_out_of_range`, also used for a value below a schema `minimum`); empty evidence; duplicate evidence ID; and malformed event ID (`malformed_event_id`, used for every event-ID field and for every `evidence` entry).
7. WHEN an S raw output passes every check in criterion 3, THE Output_Validator SHALL return, together with the parsed items, the list of person IDs and the list of event IDs that appear in the output but not in the Frozen_Context. Each list SHALL be sorted ascending and free of duplicates, and SHALL be empty when every reference exists. The verdict stays non-Illegal, so that the Grader can raise `invented_person` and `invented_event_id`.
8. THE Output_Validator SHALL return a verdict without panicking and without aborting the process for every input string, including the empty string, whitespace only, truncated JSON, an input of at least 1,048,576 bytes, and JSON nested at least 10,000 levels deep.
9. THE Output_Validator SHALL take as input a Frozen_Context type that contains no field of the Card's answer key (`acceptable`, `severe_patterns`, `expected` or any other grading field), so that the game can build the same type from simulation state.
10. FOR ALL schema-valid S outputs, parsing the output, serializing the parsed value to canonical JSON, and parsing that JSON again SHALL produce a value equal to the first parsed value (round-trip property).
11. FOR ALL Frozen_Contexts and all answers built only from the Frozen_Context's own option IDs, person IDs and event IDs with legal enum values, and written in the answer format fixed in design, THE Output_Validator SHALL return a non-Illegal verdict with empty missing-person and missing-event lists.
12. FOR ALL raw outputs that put, in an integer field, a JSON number with a fraction part or an exponent part (including values such as `1.0` and `1e2`), THE Output_Validator SHALL return an Illegal verdict with a reason code that identifies a non-integer value.
13. FOR ALL pairs of a raw output and a Frozen_Context, THE Output_Validator SHALL return identical verdicts, reason codes, parsed values and missing-ID lists on every call, and identical results whether it runs as native Rust or through Sim_Wasm.
14. IF a raw output of either Task_Type contains a JSON object with two or more members of the same key, THEN THE Output_Validator SHALL return an Illegal verdict with the reason code that identifies a parse failure.
15. IF a D raw output parses as JSON but is not an object, lacks the member `option`, holds a member other than `option`, or holds an `option` value that is not a string, THEN THE Output_Validator SHALL return an Illegal verdict with a reason code that identifies the failed D schema check (missing required field, unknown field or `wrong_type`). Membership of the `option` value in the Card's option IDs SHALL be checked by the Output_Validator only, and SHALL NOT be assumed from any constraint applied by a Runtime during decoding.
16. Amendment (Requirement 19): WHERE the raw output is a Raw_Choice of the System_One_Shape, THE Output_Validator SHALL accept the Raw_Choice string in place of the JSON object of criterion 2 and SHALL decide legality by exact string comparison with the Frozen_Context's option IDs; criteria 4, 5, 8, 13 and 14 keep their meaning, and no other member or JSON parsing applies to a Raw_Choice. The mode is selected by the Response_Shape of the Combination, never by the content of the output.

### Requirement 5: Grader in `sim-core`

**User Story:** As the developer, I want grading done exactly as the cards README defines it, in one deterministic place, so that every Metric is computed from the same Grades.

#### Acceptance Criteria

1. THE Grader SHALL live in `sim-core` with the same restrictions as the Output_Validator: integers only, no I/O, no clock reads and no randomness.
2. THE Grader SHALL take as input one Output_Validator verdict (a parsed answer or an Illegal verdict) and one Card's answer key, and SHALL return the same Grade every time it is given the same verdict and the same answer key.
3. WHEN grading a non-Illegal D answer, THE Grader SHALL set acceptable if and only if the chosen option ID is in the Card's `acceptable` list, SHALL set severe if and only if the chosen option ID is in the Card's `severe` list, SHALL clear illegal, and SHALL return an empty list of severe conditions.
4. WHEN grading an Illegal answer of either Task_Type, including a Timeout or a runtime error, THE Grader SHALL set illegal, clear acceptable, clear severe, return an empty list of severe conditions, and run no severe check.
5. WHEN grading a schema-valid S answer, THE Grader SHALL clear illegal and SHALL set acceptable if and only if every `must_include` pattern has a Pattern_Match with at least one item and no item has a Pattern_Match with any `must_not_include` pattern. Items that match no pattern SHALL NOT change acceptable.
6. WHEN grading a schema-valid S answer, THE Grader SHALL raise an Automatic_Severe condition only if that condition is listed in the Card's `severe_conditions` and it holds. `invented_event_id` holds when any event ID in the answer is not in the Card. `invented_person` holds when any person ID in the answer is not in the Card. `self_reference` holds when an item's two person fields hold the same person ID. The two person fields are `from`/`to` in `grudge_v1`, `debtor`/`creditor` in `debt_chain_v1`, `promisor`/`promisee` in `broken_promise_v1`, and `a`/`b` in `relationship_shift_v1`.
7. WHEN grading a schema-valid S answer, THE Grader SHALL raise a Pattern_Severe condition only if that condition is listed in the Card's `severe_conditions` and at least one item has a Pattern_Match with a `severe_patterns` entry for that condition.
8. WHEN grading a schema-valid S answer, THE Grader SHALL set severe if and only if at least one severe condition is raised. Each raised condition SHALL appear exactly once in the Grade's list of severe conditions, in an order that depends only on the set of raised conditions.
9. WHEN deciding whether an answer falls in a Contrast_Pair's expected subset, THE Grader SHALL use the cards README rule. For D, the answer falls in the subset if and only if the chosen option ID is in it. For S, the answer falls in the subset if and only if every `include` pattern has a Pattern_Match with at least one item and no item has a Pattern_Match with any `exclude` pattern. An Illegal answer SHALL fall in neither expected subset.
10. WHEN computing the Identity_Value of an answer, THE Grader SHALL use the identity fields per schema from the cards README. `grudge_v1` uses from, to and level. `debt_chain_v1` uses debtor, creditor, origin_event, status and amount. `broken_promise_v1` uses promisor, promisee, promise_event and status. `relationship_shift_v1` uses the unordered pair {a, b}, direction and turning_point. The S Identity_Value SHALL be a set, so two items with equal identity tuples count once. The Grader SHALL return `invalid` for an Illegal answer and the chosen option ID for a non-Illegal D answer.
11. IF a Card's answer key names a severe condition other than the seven Automatic_Severe and Pattern_Severe conditions, or a pattern names a field that is not in the Card's family output schema, THEN THE Grader SHALL return an error identifying the Card and the faulty entry, and SHALL NOT return a Grade for that answer.
12. FOR ALL schema-valid S answers, reordering the answer's items, or reordering the event IDs within any item's `evidence`, SHALL leave the Grade and the Identity_Value unchanged (invariance property).
13. FOR ALL Dev_Cards of Task_Type S, a schema-valid answer that uses only the Card's own person IDs and event IDs and has, for each `must_include` pattern, one item whose fields take values that pattern allows, with no item having a Pattern_Match with any `severe_patterns` entry or `must_not_include` pattern, SHALL grade as acceptable, not severe and not illegal (gold self-check).
14. FOR ALL Dev_Cards of Task_Type D, an answer choosing any option ID from the Card's `acceptable` list that is not in its `severe` list SHALL grade as acceptable, not severe and not illegal (gold self-check).
15. THE Grader SHALL be covered by `proptest` property tests for criteria 12, 13 and 14 of this requirement and for criteria 8, 10, 11 and 12 of Requirement 4. These tests SHALL run under `cargo test --workspace` and fail the gate when any property fails.

### Requirement 6: Validator and Grader reachable from TypeScript through `sim-wasm`

**User Story:** As the developer, I want the TS runner and later the browser game to call the Rust validator and grader, so that there is one implementation of the rules.

#### Acceptance Criteria

1. THE `sim-wasm` crate SHALL export functions that take JSON text inputs and return JSON text results, and together they SHALL cover these operations: running the Output_Validator on one raw model output for one Frozen_Context, running the Grader on one validated answer for one Card, computing the Identity_Value of one answer for one Card, and computing the Direction_Consistent decision for one Contrast_Pair.
2. THE Probe_Runner SHALL obtain every validity verdict, Grade, Identity_Value and Direction_Consistent decision from the `sim-wasm` exports listed in criterion 1, and SHALL write each one to Results unchanged from the value the export returned.
3. THE Probe_Runner source SHALL contain no second implementation of these rules: JSON parsing of model output for legality, option-ID membership, family output schema checks, Automatic_Severe and Pattern_Severe detection, Pattern_Match, acceptable-set membership, Identity_Value computation, and Direction_Consistent computation.
4. THE Gates_Script SHALL run a parity test over every Dev_Card. For each Dev_Card the test SHALL use a fixed, committed set of synthetic raw outputs, built from that Dev_Card's answer key and a fixed list of mutations, that contains at least one output the Output_Validator accepts and at least one output it marks Illegal. The test SHALL require the native `sim-core` build and the Sim_Wasm build to return byte-identical result JSON for every export in criterion 1.

6. WHEN the same export is called twice with byte-identical input JSON in the same build, THE `sim-wasm` crate SHALL return byte-identical result JSON both times.

IF an export receives input text that is not valid JSON or does not match the input shape that export expects, THEN THE `sim-wasm` crate SHALL return a JSON result indicating an input error without panicking or trapping, and later calls to any export in the same loaded module SHALL still return correct results.

### Requirement 7: Prompt rendering and Shuffle_Test Permutations

**User Story:** As the developer, I want prompts rendered from the frozen context only, with the shuffle permutations built in, so that order sensitivity is measured the way the cards define it.

#### Acceptance Criteria

1. THE Prompt_Renderer SHALL build each prompt only from the Frozen_Context, one Prompt_Template and one Permutation. The text of a Card's `id`, `scenario_group`, `split`, `scored`, `contrast`, `author_note`, `acceptable`, `severe`, `gold`, `severe_conditions` and `severe_patterns` fields SHALL NOT affect the prompt. Test: change any of these fields on a Card, keep its `task`, `family` and Frozen_Context the same, and the rendered prompt bytes for each Permutation stay identical.
2. WHEN given the same Frozen_Context, the same Prompt_Template bytes and the same Permutation, THE Prompt_Renderer SHALL produce byte-identical prompt text. This SHALL hold across separate runs and processes, and SHALL not depend on the Runtime, the model, the wall clock or environment variables.
3. WHEN building D Permutations for a Card with 2 to 5 options, THE Prompt_Renderer SHALL produce the base order, then the reversed order, then the order rotated by one, then the order rotated by two. It SHALL check them in that fixed order and drop every Permutation equal to the base or to an earlier kept Permutation. As a result, a 2-option Card yields exactly 1 non-base Permutation (reversed), and a Card with 3, 4 or 5 options yields exactly 3 non-base Permutations.
4. WHEN building S Permutations, THE Prompt_Renderer SHALL apply the same three fixed Permutations, in the same order as for D, to the events inside each block of events sharing one tick. It SHALL leave the order of the blocks and the order of events in single-event blocks unchanged. It SHALL drop every Permutation whose resulting event order equals the base or an earlier kept Permutation.
5. FOR ALL Cards and Permutations, the multiset of options (D) or events (S) in the rendered prompt SHALL equal the multiset in the base prompt, and for S the sequence of event ticks in the rendered prompt SHALL equal the sequence in the base prompt (invariant property).
6. THE Prompt_Renderer SHALL render every option ID, person ID and event ID character for character as written in the Frozen_Context, and SHALL render every option ID and event ID of the Frozen_Context at least once, so that the Output_Validator can check every reference against the Frozen_Context.
7. THE Probe_Runner SHALL record with every output the Template_Hash of the Prompt_Template that rendered it (the sha256 of the template bytes used for that request), and the name of the Permutation used (base, reversed, rotated by one or rotated by two).
8. IF a Card yields no non-base Permutation (for example an S Card whose blocks each hold a single event), THEN THE Probe_Runner SHALL run that Card in its base Permutation only, record that it has 0 Shuffle_Test Permutations, and SHALL not count any Flip for it.
9. IF a D Card has fewer than 2 or more than 5 options or a repeated option ID, or a Frozen_Context lacks a structural value that the Prompt_Template requires (any value other than the optional fields of criterion 11, for example an event's ID or tick, a person's ID, or the family's schema name), THEN THE Prompt_Renderer SHALL return a render error naming the Card ID and the reason, and SHALL not send any request for that Card. In a Dev_Run the Probe_Runner SHALL record the Card as not run, SHALL not record it as Illegal, and SHALL continue with the remaining Cards. In a Locked_Run Requirement 3 criterion 15 applies.
10. THE Prompt_Renderer SHALL render the Frozen_Context's tick as the current day and, for every event that has a `due_tick`, SHALL append to that event's line the text `due day N`, where N is the `due_tick`. FOR ALL Frozen_Contexts and Permutations, the decimal text of the context tick and of every event's `due_tick` SHALL appear literally in the rendered prompt.
11. WHEN an optional field of the Frozen_Context (`player_input`, `subject` or `relations`) is `null`, absent or empty, THE Prompt_Renderer SHALL render that field as `none` and SHALL NOT return a render error for it.

### Requirement 8: Adapter_Interface, Timeout and fallback

**User Story:** As the developer, I want every runtime behind one interface with the same timeout and fallback, so that the probe compares runtimes fairly and the game can reuse the adapters.

#### Acceptance Criteria

1. THE Adapter_Interface SHALL define one call that takes a prompt and request options (at least the Timeout and the sampling parameters) and returns exactly one of three results: (a) the raw output text together with its latency, (b) a Timeout, or (c) an error with a reason code. The latency SHALL be a whole number of milliseconds, measured from the moment the request is handed to the Runtime until the complete output is received.
2. WHEN a request has not completed within the Timeout, THE Runtime_Adapter SHALL return a Timeout result no later than 500 ms after the Timeout expires, and SHALL not return that request's output text as the result of the call, even if the text arrives later. After returning the Timeout result, THE Runtime_Adapter SHALL let the Runtime keep generating that request until the Generation_Cap and SHALL then interrupt the generation.
3. THE Probe_Runner SHALL use a Timeout of 10,000 ms unless the run configuration sets another value, and SHALL record the Timeout value in effect with every output it writes to the Results.
4. IF the run configuration sets a Timeout that is not a positive whole number of milliseconds, THEN THE Probe_Runner SHALL refuse to start the run, report an error naming the invalid Timeout value, send no requests, and write no Results for that run.
5. WHEN a Runtime_Adapter returns a Timeout or an error, THE Probe_Runner SHALL record that output as Illegal with the Timeout or the error reason code as the reason. In the probe this Illegal record stands in for the Rules_Default the game would use. This criterion SHALL NOT apply to these causes: an exhausted Request_Budget, which SHALL be recorded as not run with reason `budget`; a missing approval, which SHALL be recorded as not run with reason `not_approved`; and WebGPU on a hardware GPU being unavailable (`gpu_unavailable`), which SHALL be recorded as a failure result for the Combination under Requirement 9 criterion 6. None of these three SHALL count as Illegal or enter any Metric. This criterion SHALL NOT apply either to a `runtime_stuck` error or to the remaining runs of a Combination whose engine rebuild failed; criterion 13 covers both.
6. IF a Runtime cannot accept a request (for in-browser Runtimes, WebGPU is unavailable; for Workers_AI, the Workers_AI_Token is missing or empty, or the Request_Budget is exhausted), THEN THE Runtime_Adapter SHALL return an error with a reason code that names the cause, without sending the request, and the request SHALL not count against the Request_Budget.
7. THE fallback chain code SHALL try the links in a fixed order: the in-browser Runtime, then Workers_AI, then the Rules_Default. WHEN a link returns a Timeout or an error, or returns output text that the Output_Validator rules Illegal, THE fallback chain code SHALL move on to the next link. When a link returns output the Output_Validator accepts, the chain SHALL stop and try no later link.
8. WHEN the fallback chain code produces a final answer, THE fallback chain code SHALL record which link produced it (in-browser Runtime, Workers_AI or Rules_Default). For each link it tried, it SHALL also record the result kind: valid output, Illegal output, Timeout or error with its reason code.
9. THE Runtime_Adapters and the fallback chain code SHALL be covered by Unit_Tests that use a fake Runtime and make no network requests. The Unit_Tests SHALL cover at least these cases: a Timeout, an error, Illegal output text, a Runtime that cannot accept a request, a valid answer from each of the first two links, and a chain where every model link fails and the Rules_Default is used.
10. THE Runtime_Adapter for each Runtime SHALL report the Runtime name, the Runtime version and the model ID for the Model_Fingerprint. IF any of these three values cannot be determined, THEN THE Runtime_Adapter SHALL report that value as unknown rather than leave it out.
11. THE Adapter_Interface SHALL be transport-neutral: its call, request options and results SHALL contain no field specific to the Workers AI REST API, the local runner, the `env` file or the Workers_AI_Token, so that a later spec can plug a different server transport (for example a deployed Worker proxy) in behind the same Adapter_Interface without changing the fallback chain code.
12. WHEN the complete raw output text of a timed-out request arrives after the Timeout and no later than the Generation_Cap, THE Runtime_Adapter SHALL hand it to the Probe_Runner as a Late_Answer with its latency in whole milliseconds measured from the moment the request was handed to the Runtime. The Late_Answer SHALL NOT change the call's Timeout result.
13. IF the Runtime has not stopped generating a timed-out request by the Idle_Cap, THEN THE Runtime_Adapter SHALL record that no Late_Answer exists for that request and SHALL return an error with reason code `runtime_stuck` for every later request of the same engine until the engine has been rebuilt. The timed-out request itself SHALL stay recorded as a Timeout (Illegal) under criterion 5. Before it sends the next request of that Combination, THE Probe_Runner SHALL rebuild the engine and run the Warm_Up_Prompts (Requirement 9 criterion 12). IF the rebuild fails, THEN THE Probe_Runner SHALL record one failure result for the whole Combination (listed in the Report under Requirement 15 criterion 7) and SHALL record none of that Combination's remaining Card × Permutation runs as Illegal or in any Metric. Because the engine is rebuilt first, a `runtime_stuck` error record is not expected in normal operation; IF one occurs, THEN THE Probe_Runner SHALL record it as an engine fault that is not graded, not counted as Illegal and kept out of every Metric, and THE Report SHALL list it.

### Requirement 9: In-browser Runtime_Adapters (WebLLM and transformers.js)

**User Story:** As the Author, I want both in-browser engines measured on my laptop's GPU, so that the report shows whether a player's browser can run the model.

#### Acceptance Criteria

1. THE repository SHALL contain a Runtime_Adapter for WebLLM and a Runtime_Adapter for transformers.js. Each SHALL implement the Adapter_Interface and run the model's forward pass on WebGPU on a hardware GPU, with no CPU, WebAssembly-only or Software_Adapter execution of the forward pass used in any recorded result. Each SHALL be allowed to run tokenization, sampling and grammar masking on the CPU. "On WebGPU" means: the Runtime's WebGPU backend is selected for the model session (for transformers.js, the ONNX Runtime WebGPU execution provider); the Runtime's operator or node placement is logged for the session with the detection method fixed in design; and every node placed on the CPU is flagged in the Results header and the Report with its operator type and count. A Combination with nodes placed on the CPU SHALL be flagged, not failed, because the game meets the same fallback; Requirement 15 criteria 11 and 12 set how the Report presents it.
2. THE Report SHALL state, for every candidate model listed for an in-browser Runtime, the model's VRAM need in MiB and the source of that figure: either the model host's documentation, with its URL (for WebLLM, `vram_required_MB` of the pinned version's prebuilt model list), or a measurement on the Target_Machine (for transformers.js, the VRAM_Preflight peak).
3. IF a candidate model's VRAM need is greater than 2,600 MiB or is unknown, or its published text-path download is greater than 1,536 MiB, or its parameter count is greater than 2.3 billion (the In_Browser_Size_Limits), THEN THE Probe_Runner SHALL not run that model, and THE Report SHALL list the model as excluded, with the exceeded limit and its value, or "unknown", as the reason.
4. IF a candidate model fails to load or runs out of GPU memory on the Target_Machine, THEN THE Probe_Runner SHALL record a failure result for that Combination with the error message, whether it failed while loading or during inference, and the number of Cards answered before the failure. THE Probe_Runner SHALL then continue with the next Combination, and THE Report SHALL list the failure with its message.
5. WHEN an in-browser run starts, THE Runtime_Adapter SHALL record the WebGPU adapter's vendor, architecture, device and description strings as the browser reports them, and SHALL include them in the Model_Fingerprint of every result from that run. THE Report SHALL state for each in-browser Combination which GPU was used: the NVIDIA discrete GPU or the Intel integrated GPU.
6. IF the browser has no WebGPU support, returns no WebGPU adapter, or returns only a Software_Adapter when an in-browser run starts, THEN THE Runtime_Adapter SHALL return an error without falling back to another execution path, and THE Probe_Runner SHALL record a failure result for that Combination stating that WebGPU on a hardware GPU was unavailable.
7. WHEN an in-browser Runtime_Adapter loads a model, it SHALL fetch the model weights from the model host at run time. The Deploy_Directory SHALL contain no file whose sha256 equals the sha256 of any weight file fetched in a recorded in-browser run.
8. THE Probe_Runner SHALL screen every in-browser candidate model against the In_Browser_Size_Limits, measured on the `q4f32_1` build for WebLLM and the `q4` build for transformers.js, because the Target_Machine is the upper bound of the hardware a demo visitor may have and these are the builds a visitor whose GPU lacks `shader-f16` receives.

Amendment (Requirement 19): for the System_One_Shape the outcome text is the Raw_Choice (Requirement 19 criterion 8).

### Requirement 13: Quality Metrics and intervals

**User Story:** As the Author, I want each combination scored against the locked thresholds with honest intervals, so that I can tell a strong pass from a weak one.

#### Acceptance Criteria

1. THE Probe_Runner SHALL compute, per Combination and per Task_Type, over the base-Permutation outputs of Scored_Cards that are not Void_Cards: the acceptable rate (count of outputs graded acceptable divided by the count of all Scored_Cards of that Task_Type in the run's split that are not Void_Cards, whether or not they have a recorded output), the severe count (count of outputs graded severe) and the illegal rate (count of Illegal outputs divided by the same count). Illegal outputs, including Timeouts and runtime errors, SHALL be counted as not acceptable and not severe, and SHALL stay in the denominator. For a Locked_Run the denominator SHALL be the count of all Locked_Cards of that Task_Type that are Scored_Cards and not Void_Cards.
2. THE Probe_Runner SHALL compute the Shuffle_Test flip rate per Combination and Task_Type as the total count of Flips divided by the total count of non-base Permutations run, over Scored_Cards that are not Void_Cards. A Permutation whose output is Illegal SHALL count as a Flip when the base Identity_Value is not `invalid`, and SHALL NOT count as a Flip when the base Identity_Value is also `invalid`.
3. THE Probe_Runner SHALL compute contrast direction consistency per Combination and Task_Type as the count of Direction_Consistent Contrast_Pairs divided by the count of Contrast_Pairs counted, where a Contrast_Pair is counted only when both its Cards are Scored_Cards and neither is a Void_Card. A Contrast_Pair with an Illegal base output on either Card SHALL count as not Direction_Consistent. THE Probe_Runner SHALL report both counts next to the ratio.
4. THE Probe_Runner SHALL report, for every Metric, the numerator and the denominator as integers next to the rate, and SHALL compare each Metric with its Threshold exactly on those integer counts, with no rounding: acceptable rate at least 80% (inclusive), severe count at most 1 (inclusive), flip rate at most 5% (inclusive), contrast consistency at least 80% (inclusive). It SHALL report pass or fail per Metric. A Combination and Task_Type SHALL pass only when all four of those Thresholds hold. The illegal rate SHALL be reported without a pass or fail verdict.
5. IF a Metric's denominator is 0 for a Combination and Task_Type, THEN THE Probe_Runner SHALL report that Metric as not computable rather than as a rate, and SHALL report that Combination and Task_Type as not passing.
6. THE Probe_Runner SHALL report the Random_Baseline next to every D acceptable rate, as a percentage. It SHALL be computed as the mean, over the Scored_Cards of Task_Type D in the run that are not Void_Cards, of the number of acceptable option IDs in the answer key divided by the number of options. The Random_Baseline SHALL depend only on the Cards of the run and not on any model output.
7. THE Probe_Runner SHALL report, for the acceptable rate and the illegal rate of each Combination and Task_Type: the Cluster_Bootstrap interval (10,000 resamples of whole scenario groups with replacement, seed 20261104, 2.5th and 97.5th percentiles); the 95% Wilson_Interval; and the estimated intra-group correlation. Where the intra-group correlation cannot be estimated, for example with a single scenario group or zero variance, it SHALL be reported as not estimable. For contrast consistency it SHALL report a bootstrap interval over Contrast_Pairs with the same resample count, seed and percentiles.
8. WHEN the Cluster_Bootstrap and the pair bootstrap each run twice with the seed 20261104 on the same Grades, THE Probe_Runner SHALL produce bit-identical interval bounds both times.
9. WHEN the acceptable rate or the contrast consistency of a Combination and Task_Type passes its Threshold, THE Report SHALL label that Metric by the lower bound of its bootstrap interval (Cluster_Bootstrap for the acceptable rate, pair bootstrap for contrast consistency): "pass" when the lower bound is at or above the Threshold; "pass (interval overlaps threshold)" when the lower bound is below the Threshold by at most the Weak_Evidence_Margin of 10 percentage points; and "pass with weak evidence" when the lower bound is more than 10 percentage points below the Threshold. Each of these labels SHALL count as a pass under criterion 4. A Metric that fails its Threshold SHALL be reported as a failure whatever its interval.
10. THE Probe_Runner SHALL report each Sanity_Card's Grade per Combination in a separate section. Sanity_Cards SHALL NOT appear in the numerator or denominator of any Metric, in the Random_Baseline, or in any interval, and SHALL NOT affect any pass or fail verdict.
11. THE statistics code SHALL be covered by Unit_Tests that check the Wilson_Interval against known values to within 0.0005 on each bound. These values SHALL include 8 of 10 (about 0.4902 to 0.9433), 0 of 10 (lower bound 0) and 10 of 10 (upper bound 1). The Unit_Tests SHALL also check every Metric definition in criteria 1 to 6 against hand-computed examples, including an example with an Illegal output, a Void_Card, a Sanity_Card and a zero denominator.
12. THE Probe_Runner SHALL report, per Combination and Task_Type, a "quality without timeout" acceptable rate, severe count and illegal rate, computed as in criterion 1 with the same denominator but grading each timed-out request's Late_Answer, where one exists, in place of its Timeout. These figures SHALL be labelled as without timeout, and SHALL NOT affect any pass or fail mark, label or recommendation.
13. THE statistics code SHALL be covered by Unit_Tests that check the latency percentiles of Requirement 14 criterion 1 against hand-computed values for n = 60 and n = 10,000, and the weak-evidence labels of criterion 9 at lower bounds exactly at the Threshold, exactly 10 percentage points under it, and just over 10 percentage points under it.

### Requirement 14: Performance measurements

**User Story:** As the Author, I want latency, cold start, download size and memory measured per combination, so that I can judge whether a player will wait for the model.

#### Acceptance Criteria

1. THE Probe_Runner SHALL report latency p50 and p95, in whole milliseconds, per Combination and Task_Type. The latency of one request is the time from the Runtime_Adapter sending the prompt to the Runtime_Adapter receiving the complete raw text. The percentiles cover every request that returned raw text, including outputs later graded Illegal because they do not parse or fail the schema, and exclude Timeouts and runtime errors. For n covered requests sorted ascending by latency, the p-th percentile (p = 50 or p = 95) SHALL be the value at the 0-based index ceil(p·n / 100) − 1, computed with integer arithmetic only (nearest-rank).
2. THE Probe_Runner SHALL report three counts next to the latency percentiles of each Combination and Task_Type: the number of requests the percentiles cover, the number of Timeouts, and the number of runtime errors.
3. IF no request of a Combination and Task_Type returned raw text, THEN THE Probe_Runner SHALL report "no data" in place of p50 and p95 and SHALL still report the three counts from criterion 2.
4. THE Probe_Runner SHALL report cold start, in whole milliseconds, for each in-browser Combination on the Target_Machine, measured twice at the start of that Combination's Locked_Run in a Fresh_Profile created for that Combination. Empty cache: the Fresh_Profile holds no model or Runtime files in its HTTP cache or site storage, and cold start runs from the start of the model download to receipt of the complete raw text of the first Warm_Up_Prompt answer. Warm cache: the same Fresh_Profile and browser context, right after the empty-cache measurement, with the page reloaded, and cold start runs from the start of model loading to receipt of the complete raw text of the first Warm_Up_Prompt answer. THE Probe_Runner SHALL delete the Fresh_Profile directory after the Combination's run.
5. THE Probe_Runner SHALL report, for each in-browser Combination, the total bytes transferred over the network during the empty-cache cold start measurement. The model files and the Runtime files are reported separately, each in bytes and in MiB rounded to one decimal place.
6. THE Probe_Runner SHALL report "not applicable" for cold start and download bytes for every Workers_AI Combination.
7. WHERE a Runtime makes a memory measurement available, THE Probe_Runner SHALL report peak memory per Combination in MiB, measured during that Combination's Locked_Run, and name the quantity measured. For the Intel integrated GPU, THE Probe_Runner SHALL either report the quantity as "Chrome GPU process peak RSS (excludes unmapped GEM buffers)" or measure GPU memory through i915 debugfs or `intel_gpu_top` and name that source; otherwise it SHALL report "not measured". Intel integrated GPU figures SHALL NOT be reported in the same table column as NVIDIA discrete GPU figures. Where no measurement is available, THE Probe_Runner SHALL report "not measured" together with the reason.
8. THE Report SHALL state the Target_Machine; the full browser version string; the network conditions of the download measurements (the connection type, whether throttling was applied, and the throttled or measured download bandwidth); and the Workers_AI region or endpoint, where the API reports one.
9. WHEN an in-browser Combination is about to download its model in a Fresh_Profile, THE Probe_Runner SHALL read the page origin's storage quota as the browser reports it. IF the quota is not greater than the Combination's expected download in bytes, THEN THE Probe_Runner SHALL download nothing, SHALL record a failure result `model_load_failed` with reason `quota` and the quota and expected values, and SHALL continue with the next Combination.
10. THE cold start, download bytes and peak memory figures that the Report uses SHALL come from the measurements of criteria 4, 5 and 7 taken during the Combination's Locked_Run.

### Requirement 15: Report and decision

#### Acceptance Criteria

1. THE Report SHALL contain, for every Combination with a completed Locked_Run and for each Task_Type in that Locked_Run's Task_Type_Subset: every Metric from Requirement 13 with its Threshold and a pass or fail mark; the Cluster_Bootstrap interval and Wilson_Interval for the acceptable rate and the illegal rate, plus the bootstrap-over-pairs interval for contrast consistency; the Random_Baseline next to every D acceptable rate; the Sanity_Card results, shown apart from the Metrics; and every performance figure from Requirement 14, including "not measured" entries with their reasons.
2. THE Report SHALL take every Metric, interval and performance figure it uses for a recommendation from Locked_Run Results only. Any Dev_Run figure the Report shows SHALL be labelled as a Dev_Run figure and SHALL be kept out of the pass or fail marks and out of the recommendation.
3. THE Report SHALL give one recommendation per Task_Type (D and S). Each recommendation SHALL name the recommended Combination for each link of the fallback chain in-browser Runtime, then Workers_AI, then Rules_Default, or SHALL state that the link has no recommended Combination.
4. THE Report SHALL mark each link of the fallback chain, per Task_Type, as supported, not supported, or, for the Workers_AI link only, "not measured (browser passed)" under Requirement 18 criterion 3. A Runtime link counts as supported only when at least one Combination of that Runtime passed for that Task_Type under Requirement 13 criterion 4 in the Locked_Run_Ledger entry used under Requirement 3 criterion 8, and, for an in-browser Runtime, that Combination has no Exclusion_Record and is not marked over the In_Browser_Size_Limits (Requirement 9 criteria 11 and 17). 5. IF no Combination of any Runtime passes for a Task_Type, THEN THE Report SHALL recommend the Rules_Default alone for that Task_Type and SHALL list, for each Combination run, which Thresholds failed.
6. THE Report SHALL record, for every model run and every Runtime library used, the license name and the URL of the source that states the license. ### Requirement 16: Gates, fault injection and licenses

**User Story:** As the developer, I want every new check in the offline gates and proven to fail once, so that the probe's foundations stay correct without network, GPU or spending.

#### Acceptance Criteria

1. THE Gates_Script SHALL run each of the following checks on every invocation: the Manifest_Check, the Output_Validator tests and the Grader tests (through `cargo test --workspace`), the native-versus-WASM grading parity test, the Probe_Runner Type_Check, the Probe_Runner Unit_Tests, the Deploy_Directory token-reference check, the Deploy_Directory Card and Results marker check (Requirement 3 criterion 13), and the `web/`-imports-`eval/` check (Requirement 3 criterion 16).
2. THE Deploy_Directory token-reference check SHALL fail if any file in the Deploy_Directory contains the string `WORKERS_AI_TOKEN` or the Workers AI API host name (Requirement 11 criterion 10), and SHALL pass when no file in the Deploy_Directory contains either.
3. IF any check run by the Gates_Script fails, THEN THE Gates_Script SHALL exit with a non-zero status and SHALL name the failing check in its output.
4. THE Gates_Script SHALL complete with exit status 0 on a machine with no network route to any model host or to Workers_AI, no GPU, and no Workers_AI_Token, including when the root file `env` is absent or does not define `WORKERS_AI_TOKEN` or `CLOUDFLARE_ACCOUNT_ID`.
5. THE Gates_Script SHALL send zero requests to any Runtime, and SHALL not download any model file or count against the Request_Budget.
6. WHEN this spec adds a check to the Gates_Script, THE developer SHALL inject the fault that check guards against (at least one fault per new check, for example a wrong Pinned_Manifest_Hash constant in source code, a Grader that ignores `must_not_include`, a type error in the Probe_Runner, or the string `WORKERS_AI_TOKEN` placed in a Deploy_Directory file), run the Gates_Script and confirm that it exits non-zero and names that check, revert the injection, and confirm that the Gates_Script exits 0 again.
7. WHEN a fault-injection run from criterion 6 is finished, THE developer SHALL record in `docs/kiro-log.md` the check under test, the injected fault, the name of the failing check reported by the Gates_Script, and that the Gates_Script passed after the revert. Each entry is written when the run happens and is never backfilled.
8. THE `README.md` SHALL list every third-party library this spec adds as a direct dependency in any `Cargo.toml` or `package.json`, including WebLLM, transformers.js and any statistics or schema library. Each entry SHALL give the library name, the exact version resolved in `Cargo.lock` or `pnpm-lock.yaml`, and the license as an SPDX identifier.
9. THE Gates_Script SHALL keep running every gate that existed before this spec, with exit status 0, and SHALL not remove or skip any of them. These gates are `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, the `rand`/`getrandom` check on `sim-core`'s normal dependency tree, the `sim-cli batch` step, the pnpm version check, the frozen-lockfile install, the web Type_Check, the web Unit_Tests, the Web_Build with its Size_Limit, `.wasm` byte-identity and main-bundle boundary checks, and the Smoke_Test.
10. THE developer SHALL show the Manifest_Check gate failing by injecting a wrong Pinned_Manifest_Hash constant, and SHALL inject no fault by editing, creating or deleting any file under `eval/cards/`. File-level Manifest faults (an edited, missing or extra file) SHALL be covered by Unit_Tests that run the Manifest_Check on a temporary copy of the Card_Set outside `eval/cards/`.
11. THE developer SHALL show the `web/`-imports-`eval/` check of Requirement 3 criterion 16 failing by injecting, in a file under `web/`, an import of a path under `eval/` with a `?raw` suffix, and SHALL record the injection and revert under criterion 7.

### Requirement 17: Process and approvals

WHEN a Locked_Run starts, THE developer SHALL append a `docs/kiro-log.md` entry with the Combination, the Task_Type_Subset, the Model_Fingerprint and the Pinned_Manifest_Hash before the first request of that run is sent. 7. THE developer SHALL make no change to any file under `eval/cards/`, so that `git diff` of `eval/cards/` against the import commit `091d1d7` is empty at every commit of this spec.
