# Requirements Document

## Introduction

Spec 6 of Back in the Family delivers the first playable version: the thinnest vertical slice that runs the whole loop in the browser, with rules only and no model call. The player starts as a mid-life adult, meets a few interruptions with concrete stakes, dies, sends one template-text dream from the Underworld, plans and claims a rebirth path, is reborn, and the second life keeps running. Every module stays thin; later specs thicken them. Target: 3 to 5 days in total.

The spec spans `sim-core` (Narrator, Player_Nodes, Chronicle, Rebuilt_Body customization, Path_Status), `sim-cli` (Playthrough_Branch, narrator metrics, gates), `sim-wasm` (Snapshot and input extensions) and `web` (clock-paced play, Town_View, scene templates, Chronicle_Panel, Choice_Panel, Underworld_Panel, Worker_Protocol extensions). It is one spec with checkpoints in the task plan (Author, 2026-11-16, decision 1).

Citations: life-sim requirements as "LS-R<n>.<m>", underworld requirements as "UW-R<n>.<m>", web-shell requirements as "WS-R<n>.<m>". They stay in force unless a criterion here changes them.

Facts from the current code that these requirements build on:
- The existing Decision_Nodes (`dream_interpretation`, `magistrate_ruling`) fire in step 2a and resolve in step 2b of the same tick; an External_Choice names its node by the trigger input's `seq` (`NodeRef::Trigger`). `Nodes::pending` is empty at every tick boundary.
- Current behaviour, which this spec changes (Requirement 8): the Sim_Worker runs `Speed` ticks per Frame (WS-R4.3, WS-R4.4), with Speeds 1, 7, 30, 90 and 365 and a default Speed of 1; Frames come from `requestAnimationFrame` or a 16 ms timer, so the default Speed runs about 60 ticks per second on a 60 Hz display and about 120 on a 120 Hz display.
- Persons have seven Traits and no interests field. Debts carry a `due` tick. Events carry `caused_by` pointers. The card event-type list includes `promise`, `promise_kept`, `will`, `inheritance`, `gift`, `help`, `quarrel`, `apology` and `offering`.
At the commit where this spec starts, the replay format is version 4 and a Rebuilt_Body claim is encoded as `{"ClaimSlot":{"slot":"RebuiltBody"}}` with no further field. This is a baseline fact, not the target contract: task 1.1 may add staged replay DTO arms without changing the version, and task 6.1 is the only task that raises `REPLAY_VERSION` from 4 to 5 and then rejects versions 2, 3 and 4.
- Default Params: `dream_price` 20, `haunt_price` 40, `imported_price` 100, `rebuilt_price` 400, `yearly_cap` 500, `player_max_wait` 1,095, `birth_lead_days` 180, `grudge_threshold` -40.
- The underworld kin-decay baseline (task 9.5, design "Offering diagnosis (H1–H5)", H1): positive kin Relations "first reach zero" after a median of 3.66 years (1,336 days) in the passive branch. It was measured by an uncommitted scratch program over kin Relations sampled as incoming Relations of Ghosts and dying Persons at deaths and Offering_Occasions; the design does not state whether a Relation that jumps from positive to negative without passing 0 counts.

Rules for this spec:
- The offering economy is unchanged (Author, 2026-11-16, decision 5): OP-U15 stays closed, no new income source, no price cut and no extra joss paper to fix reachability or to make two paths executable at death.
- Player_Nodes are a NEW cross-tick lifecycle added by the Narrator (decision 2): a node fires during tick t and resolves in tick t+1. This differs from the same-tick resolution of the existing Decision_Nodes, which this spec leaves unchanged.
- Anything that would add an economy mechanism, widen Customization or change an existing gameplay guarantee goes back to the Author.
- Out of scope: Workers AI clef, the Cloudflare Worker script and request budget, generative text, the replay gallery, the settings page, sound, scene templates beyond the four named here, the F1 append-refusal mapping, an interests field on Person, haunting and Bribe controls in the Web_App (follow-up item; their `sim-core` backends and tests stay), and a higher-grade conflict or feud escalation node (a later spec).

## Glossary

- **Life_Sim**, **Underworld**, **Sim_Cli**, **Sim_Wasm**, **Gates_Script**: as in the life-sim and underworld specs.
- **Narrator**: the `sim-core` component that scans each tick for Narrator_Candidates, applies the Interrupt_Budget and Salience rules, fires and resolves Player_Nodes and writes Chronicle_Entries.
- **Narrator_Candidate**: one match of a Pattern in one tick, with a family, the Player_Soul's body as chooser, Stakes and an option set.
- **Pattern**: one rule of the Narrator's pattern library that matches Events appended in the current tick, their One_Hop_Neighbours, or a Clock_Trigger.
- **One_Hop_Neighbour**: an Event linked to a new Event by one `caused_by` pointer in either direction, or a Person who is an actor of a new Event.
- **Clock_Trigger**: a Pattern condition that depends only on the tick and World state, not on a new Event: a Debt of the player's body reaching a set number of days before its `due` tick, or the player's body reaching a Life_Stage age.
- **Stakes**: the who (Person IDs), how much (an integer amount with its unit: money, joss paper, affinity or Trait points) and by when (a tick) of a Narrator_Candidate.
- **Player_Node**: a node fired by the Narrator during tick t, chosen for the Player_Soul's living body, with a Node ID, a closed option set of 2 to 5 options, a Rules_Default, firing tick t and resolution tick t+1.
- **Choice_Tick**: the only tick on which an External_Choice for a Player_Node fired at tick t is accepted: tick t+1.
- **Defensible_Option_Set**: an option set in which at least two legal options have Option_Previews that differ in at least one cost or effect amount.
- **Option_Preview**: for one option, the list of affected Persons with the sign and amount of each effect, computed by rules at firing.
- **Salience**: an integer score of a Narrator_Candidate computed from the candidate's ties to the Player_Soul's current body and to earlier bodies of the Player_Soul.
- **Interrupt_Budget**: the tick-counted rule that limits when a Player_Node may fire: the First_Interrupt_Band and the Interrupt_Gap.
- **First_Interrupt_Band**: the tick offsets from the start of a Player_Life at which the first Player_Node of that life is due: `first_interrupt_min <= offset < first_interrupt_max`, so with the Params of Requirement 3.1 the band is `600..=899`. `first_interrupt_max` is the exclusive upper bound (30 × Play_Rate = 900, the first offset that is no longer "within 30 s"); `first_interrupt_min` keeps the first stop at about 20 s of play or later at Speed 1, so an earlier stop does not count as ideal pacing. The 20 to 30 s figure is a wall-clock target checked by Requirement 16.11, not a tick bound.
- **Intro_Debt**: the one opening Debt of Requirement 5.2 that the Life_Sim designates at Opening_World generation to guarantee the first Player_Life's first Player_Node; a first-life onboarding rule of this spec, not a general Debt mechanism.
- **Intro_Grace**: the World state in which the Intro_Debt takes no part in repayment rolls and is never the target of the `inheritance` family's `pay_debts` effect (Requirement 5.12); its eligible `debt_due` candidate has first priority during the grace (Requirements 2.6 and 3.2). It holds from Opening_World generation until an end condition of Requirement 5.10 actually occurs.
- **Interrupt_Gap**: the minimum and target number of ticks between two Player_Node firings in the same Player_Life.
- **Play_Rate**: the number of ticks per second of wall time at Speed 1, independent of the display refresh rate: 30.
- **Speed**: the playback multiplier chosen from the list 1, 7, 30, 90 and 365; at Speed s the Sim_Worker targets s × Play_Rate ticks per second of wall time. Speed changes pace only.
- **Advance_Method**: how a player or the Smoke_Test moves fast through a life: the run control at Speed 365 combined with the automatic stops of Requirement 8.1. The Web_App adds no other fast-forward control in this spec.
- **Chronicle_Entry**: a World record of one auto-resolved Narrator_Candidate or one resolved Player_Node, with tick, family, Stakes, applied option, source (External_Choice, Rules_Default, or Auto_Resolved) and the list of skipped effect parts.
- **Life_Stage_Node**: a Player_Node of family `life_stage`, fired when the body reaches a Life_Stage age during a Player_Life, whose options bias Traits.
- **Rebuilt_Draw**: the seven uncustomized Rebuilt_Body Traits drawn once for the Player_Soul at the start of a Player_Wait and stored in World state inside the Checksum (Requirement 6.2).
- **Base_Traits**: the seven Traits a Rebuilt_Body claim would give the new body without Customization: the Rebuilt_Draw with the Carry_Over already applied.
- **Customization**: the part of a Rebuilt_Body claim that sets the body's Traits, in one of two forms: **Set** (one Trait set to a value in -3..=3) or **Adjust** (two distinct Traits, each moved by +1 or -1 from its Base_Traits value, clamped to -3..=3).
- **Rebirth_Path**: one of local newborn (Birth_Slot), Imported_Vessel and Rebuilt_Body.
- **Path_Status**: for one slot shown to the waiting Player_Soul, computed by rules: announced (visible), claimable now, affordable now, and the Needed list of what is still missing (wait until tick X, joss paper short by N, Yearly_Cap room short by N, or another named condition).
- **Executable_Path**: a slot whose Path_Status is both claimable now and affordable now. "Keep waiting" is not an Executable_Path.
- **Past_Life_Tie**: a Relation from a living Resident toward the body of an earlier Player_Life.
- **Blood_Tie**: a Kinship_Tag Relation between the player's current body and a Resident.
- **Rememberer**: a living Resident who holds a Past_Life_Tie.
- **Soul_Marker**: the single glyph and colour the Web_App uses for the Player_Soul in every Player_Life and in the Underworld.
- **Web_App**: the Svelte 5 front end under `web/`, running on the Main_Thread, with the Sim_Worker owning the only `WasmSim`.
- **Town_View**: the Canvas top-down view of the town's Households and Residents.
- **Scene_Template**: one of exactly four staging templates, `funeral`, `inheritance`, `dream` and `birth`.
- **Choice_Panel**: the DOM panel that shows a pending Player_Node with its Stakes, options and Option_Previews, used for families without a Scene_Template.
- **Chronicle_Panel**: the DOM panel that lists Chronicle_Entries as template text.
- **Underworld_Panel**: the DOM panel shown while the Player_Soul is in the Waiting_Queue: Joss_Balance, Connected_Persons, the dream input, slots with their Path_Status, Carry_Over and Customization.
- **Pause_Reason**: why the Sim_Worker stopped running: `player_node`, `player_died`, `dream_resolved`, `player_reborn`, or `user`.
- **Playthrough_Branch**: a Sim_Cli run of the Acceptance_Seeds whose Auto_Player answers Player_Nodes, makes Devoted-style in-life social acts and claims slots under a fixed strategy and budget set in design, modelling a family-minded player (Requirement 13.13); an acceptance branch only, not a production AI; its figures are report-only.
- **Playthrough_Fixture**: a Parity_Fixture recorded from a scripted playthrough input stream that crosses the Player_Soul's first death and rebirth.
- **Art_Trial**: the visual checkpoint of Requirement 12: a candidate asset pack shown on one small representative screen for the Author's decision.

## Requirements

### Requirement 1: Player_Node lifecycle

**User Story:** As the developer, I want player choices to be recorded nodes that the core resolves on its own, so that the simulation never waits for the UI and replays stay exact.

The Author decided P-1 execution scope on 2026-11-16 (Decisions section): the core never waits and never branches on an execution mode. Requirement 1.4 is the single default-resolution contract for every Player_Node, including the first, and headless, CLI and replay runs use it unchanged. The interactive Sim_Worker is the only layer that refuses to cross a Choice_Tick while a pending Player_Node has no accepted External_Choice (Requirement 8.9).

#### Acceptance Criteria

1. WHEN the Narrator fires a Player_Node during tick t, THE Narrator SHALL assign it the next Node ID from the existing Node ID counter (shared with `dream_interpretation` and `magistrate_ruling`, so no two nodes of any kind share a Node ID) and store the pending Player_Node in the World, inside the Checksum, with its family, option set of 2 to 5 option IDs, Option_Previews, Stakes, Rules_Default, firing tick t and resolution tick t+1.
2. THE Narrator SHALL fire Player_Nodes only in the Narrator step that runs after the last life-sim and underworld step of tick t, and SHALL resolve every Player_Node in tick t+1 in a fixed resolution step, set in design, that runs after the inputs of tick t+1 are accepted and before any step of tick t+1 that can end a life.
3. WHEN the resolution step of tick t+1 runs and an External_Choice for the pending Player_Node was accepted at tick t+1, THE Narrator SHALL apply the option that External_Choice names.
4. WHEN the resolution step of tick t+1 runs and no External_Choice for the pending Player_Node was accepted at tick t+1, THE Narrator SHALL apply the Rules_Default stored at firing. This is the core's only default-resolution contract and it applies to every Player_Node, including the first; the core SHALL NOT branch on an execution mode. The interactive Sim_Worker never reaches this case for a Player_Node that has no accepted External_Choice (Requirement 8.9).
5. THE Life_Sim SHALL accept an External_Choice for a Player_Node only as a TickInput for the node's Choice_Tick that names the node by its Node ID and names exactly one option ID.
6. IF an External_Choice names a Node ID that is not a pending Player_Node (including a node already resolved), names an option ID outside the node's option set, is for a tick other than the node's Choice_Tick, or names a Player_Node that already has an accepted External_Choice, THEN THE Life_Sim SHALL reject the input under LS-R1.5 and leave the pending node and its accepted choice, if any, unchanged.
7. WHEN a Player_Node resolves, THE Narrator SHALL resolve it exactly once, append exactly one Chronicle_Entry holding the resolution tick, family, Stakes, applied option ID, source (External_Choice or Rules_Default) and skipped effect parts, and remove the node from the pending set in that same tick.
8. THE Narrator SHALL compute every Rules_Default once, at the firing tick, only from World state at the firing tick, the chooser's Traits and seeded streams keyed by IDs, and SHALL not recompute it at resolution.
9. IF, at resolution, a part of the applied option's effect names a Person, Household or Debt that no longer exists or is no longer in the state that part requires, THEN THE Narrator SHALL skip that part, apply every other part, roll back no applied part, and list the skipped parts in the Chronicle_Entry of criterion 7.
10. IF the chooser body is not a living Resident when the resolution step of tick t+1 runs, THEN THE Narrator SHALL ignore any accepted External_Choice, apply the Rules_Default under criterion 9 with every effect part that names the chooser body skipped, and record source Rules_Default with the flag `chooser_absent` in the Chronicle_Entry; the Narrator SHALL never move the resolution tick. This is a safety net reached only by a constructed World or a headless run; the interactive Sim_Worker cannot reach it, because its resolution step runs before any step that can end a life (criterion 2) and it never advances an unanswered Player_Node (Requirement 8.9).
11. THE Life_Sim SHALL keep the same-tick resolution of `dream_interpretation` and `magistrate_ruling` (UW-R3, OP-U11) unchanged, including their naming of nodes by trigger `seq` and an empty `dream_interpretation`/`magistrate_ruling` pending set at every tick boundary.
12. THE Narrator SHALL keep at most one Player_Node pending at the end of every tick.

### Requirement 2: Narrator patterns and stakes

**User Story:** As a player, I want interruptions about things that matter to my soul, with concrete stakes, so that every stop names who, how much and by when.

#### Acceptance Criteria

1. WHEN the last life-sim and underworld step of a tick completes, THE Narrator SHALL compute that tick's Narrator_Candidates only from Events appended in that tick, their One_Hop_Neighbours and the Clock_Triggers whose condition first holds at that tick, reading World state as it stands after that step.
2. THE Narrator SHALL provide at least the Pattern families `family_death`, `inheritance`, `debt_due`, `feud` and `life_stage`, in that family order, with the trigger, option set and effects of each family set in design.
3. WHEN the Narrator builds a Narrator_Candidate, THE Narrator SHALL give it an option set of 2 to 5 options with distinct option IDs, mark exactly one of them as the Rules_Default, and attach one Option_Preview to every option.
4. WHEN the Narrator builds a Narrator_Candidate, THE Narrator SHALL attach Stakes with at least one Person ID of a Person present in the World at that tick, at least one integer amount with exactly one unit from money, joss paper, affinity or Trait points, and one by-when tick no earlier than the current tick.
5. THE Narrator SHALL compute every option effect only through Event types and tags in the card lists (LS-R5.3 to LS-R5.9) and through the Trait bias of Requirement 4, with every effect amount an integer.
6. WHEN several Narrator_Candidates exist in one tick, THE Narrator SHALL order them by Salience, highest first, with ties broken by the lowest triggering Event ID (a Clock_Trigger candidate ranking after every Event-triggered candidate of equal Salience) and then by the family order of criterion 2, and SHALL pass them to the Interrupt_Budget of Requirement 3 in that order, except that during Intro_Grace the Intro_Debt's eligible `debt_due` candidate ranks before every other candidate in its trigger tick if the first Player_Node of the first Player_Life has not fired (Requirement 5.16). Other candidates retain this order.
7. THE Narrator SHALL compute Salience as an integer only from the candidate's Blood_Ties, Relations, Debts and Past_Life_Ties toward the Player_Soul's current body and earlier bodies, as they stand at the tick of criterion 1, with the formula and the minimum Salience set in design.
8. IF a Narrator_Candidate's Salience is below the minimum Salience, THEN THE Narrator SHALL drop the candidate, apply none of its effects and append no Chronicle_Entry for it.
9. IF the Player_Soul has no living body at the tick of criterion 1, THEN THE Narrator SHALL produce no Narrator_Candidate in that tick.
10. THE Narrator SHALL produce at most one Narrator_Candidate per family for each triggering Event, and at most one per Clock_Trigger condition (one Debt and day count, or one body and Life_Stage age), over the whole run.
11. WHEN an Event appended in a tick leaves a Relation between the Player_Soul's body and another Resident (in either direction) with affinity below `grudge_threshold`, and that Relation's affinity was at or above `grudge_threshold` before the Event, THE Narrator SHALL produce one `feud` Narrator_Candidate for that crossing, subject to the Interrupt_Budget of Requirement 3.
12. IF a Relation's affinity was already below `grudge_threshold` before an Event, THEN THE Narrator SHALL produce no `feud` Narrator_Candidate for that Relation from that Event, so that the Relation becomes a `feud` candidate again only after it has returned to at or above `grudge_threshold` and crosses below again.

### Requirement 3: Interrupt_Budget and auto-resolution

**User Story:** As a player, I want the first stop of my first life within 30 seconds but not at once, then about one stop every 30 to 40 seconds, and no stop without a real choice, so that the pace feels right.

#### Acceptance Criteria

1. THE Narrator SHALL count the Interrupt_Budget in ticks using four Params stored inside the Checksum: `first_interrupt_max` of 30 × Play_Rate = 900 ticks, the exclusive upper bound of the First_Interrupt_Band, so an offset of 900 is outside it; `first_interrupt_min`, an integer in 600..=899 set in design, the inclusive lower bound, so that the band is `600..=899` and the first stop comes after about 20 s of play at Speed 1; the minimum Interrupt_Gap of 30 × Play_Rate = 900 ticks; and the target Interrupt_Gap of 40 × Play_Rate = 1,200 ticks. The 20 to 30 s figure is the wall-clock target of Requirement 16.11 and is not converted into a tick bound.
2. WHEN a tick's Narrator step runs while the Player_Soul is embodied and no Player_Node is pending, THE Narrator SHALL fire a Player_Node for the first Narrator_Candidate in the order of Requirement 2.6 that meets all of these conditions: its Salience is at or above the minimum Salience; it has a Defensible_Option_Set; and either it would be the first Player_Node of the current Player_Life and the tick is at least `first_interrupt_min` after the start of that life, or the tick is at least the minimum Interrupt_Gap after the firing tick of the previous Player_Node of the same Player_Life. During Intro_Grace before the first node fires, this selects the eligible Intro_Debt `debt_due` candidate first on its trigger tick (Requirement 5.16); an earlier first Player_Node is not replaced.
3. IF a Narrator_Candidate at or above the minimum Salience has no Defensible_Option_Set, THEN THE Narrator SHALL apply its Rules_Default in the same tick and append one Chronicle_Entry with source Auto_Resolved.
4. IF a Narrator_Candidate at or above the minimum Salience with a Defensible_Option_Set is not fired in its tick under criterion 2, because of `first_interrupt_min`, the minimum Interrupt_Gap, a pending Player_Node, or another candidate that fired in that tick, THEN THE Narrator SHALL apply its Rules_Default in the same tick and append one Chronicle_Entry with source Auto_Resolved, except that the Intro_Debt's eligible `debt_due` candidate SHALL NOT be auto-resolved solely because another candidate competes at its trigger tick while Intro_Grace holds and the first Player_Node has not fired (Requirement 5.16). This exception changes no rule for any other candidate.
5. THE Narrator SHALL fire Player_Nodes only under criterion 2, with no late firing, no lowered Salience and no other rule for a first interruption; the first-life guarantee comes from the opening of Requirement 5.
6. THE Narrator SHALL fire at most one Player_Node per tick.
7. THE Narrator SHALL take the start of a Player_Life as the tick at which the Player_Soul enters that life's body: the Opening_World tick for the first Player_Life, and the tick at which the claimed body becomes the current body for later Player_Lives. THE Narrator SHALL measure every Interrupt_Gap as the difference between two Player_Node firing ticks in the same Player_Life.
8. WHEN more than one Narrator_Candidate is auto-resolved in one tick under criteria 3 and 4, THE Narrator SHALL apply their Rules_Defaults one at a time in the order of Requirement 2.6, appending one Chronicle_Entry per candidate in that order, with the skip rule of Requirement 1.9 applied to each.
9. THE Life_Sim SHALL guarantee a first Player_Node inside the First_Interrupt_Band only for the first Player_Life (Requirement 5.2). For later Player_Lives the first stop comes, best effort and reported under Requirement 13.1, from `life_stage` nodes (Requirement 4) and the ordinary Pattern families for Birth_Slot bodies, and from the ordinary Pattern families and any Life_Stage age still ahead for Imported_Vessel and Rebuilt_Body bodies. THE Life_Sim SHALL create no Debt, Relation or other state in a later Player_Life for the purpose of producing a stop.

### Requirement 4: Life-stage choices

**User Story:** As a player reborn as a child, I want two or three childhood choices that nudge who I become, so that the second life starts quickly without a script.

#### Acceptance Criteria

1. THE Life_Sim SHALL store the Life_Stage ages in Params inside the Checksum as distinct day counts: two or three childhood ages, each below 6,570 days (18 years of 365 days), and zero or more adult ages, with all values set in design.
2. WHEN the body of a Player_Life reaches an age in days equal to a Life_Stage age that is greater than the body's age at the start of that Player_Life, THE Narrator SHALL produce exactly one `life_stage` Narrator_Candidate for that age in that tick, for every Origin of the body (Birth_Slot newborn, Opening_World body, Imported_Vessel or Rebuilt_Body).
3. IF a Life_Stage age is at or below the body's age at the start of the Player_Life, THEN THE Narrator SHALL produce no `life_stage` Narrator_Candidate for that age in that Player_Life, so that an adult-start body skips the childhood stages it has passed.
4. WHEN a `life_stage` option is applied, THE Life_Sim SHALL change at most two distinct Traits of the body by -1, 0 or +1 each, and SHALL clamp each resulting Trait to -3..=3, so that a change past a bound leaves the Trait at that bound.
5. WHEN a `life_stage` option is applied, THE Life_Sim SHALL change only the Traits of criterion 4, and SHALL append no Event, change no Relation, Debt, money, Household or other Person, and start no action, apart from the Chronicle_Entry of Requirement 1.7, 3.3 or 3.4.
6. THE Life_Sim SHALL keep the Person model's Traits as the only target of life-stage bias, with no interests field.
7. WHEN the Narrator builds a `life_stage` Narrator_Candidate, THE Narrator SHALL give it 2 to 5 options. Each option's Option_Preview SHALL name the body and the signed, post-clamp Trait-point change of each Trait the option changes, computed from the body's Traits at the candidate's tick. The candidate's Stakes SHALL name the body's Person ID, the largest absolute Trait-point change among its options (unit: Trait points), and the candidate's tick plus 1 as the by-when tick.

### Requirement 5: Opening for the first life

**User Story:** As a judge, I want the first life to start as an adult with family, debts and grudges, and a real first stop soon after the start, so that the first stop has stakes.

#### Acceptance Criteria

1. WHEN Opening_World generation completes for any seed, THE Life_Sim SHALL make the Player_Soul's body, at tick 0, a living Resident whose age is inside the LS-R12.5 Player_Soul opening age band (20 to 50 years inclusive, or the band as adjusted in the life-sim design) and whose Household has at least one other living Resident.
2. WHEN Opening_World generation completes for any seed, THE Life_Sim SHALL give the Player_Soul's body, at tick 0, an open Debt in which the body is debtor or creditor, the other party is a living Resident, and the `debt_due` Clock_Trigger of that Debt falls at a tick inside the First_Interrupt_Band of the first Player_Life.
3. WHEN the Life_Sim chooses the Player_Soul's body, THE Life_Sim SHALL choose, by a seeded stream, among age-band Residents who meet criterion 1 and already hold a Debt that meets criterion 2; IF none exists, THEN THE Life_Sim SHALL choose, by a seeded stream, among age-band Residents who meet criterion 1 and hold an open Debt or a Relation with affinity below `grudge_threshold` (strictly less than, as in LS-R12.4), else among all who meet criterion 1, and SHALL add one real Debt between the chosen body and a living Resident at Opening_World generation so that criterion 2 holds.
4. WHEN the `debt_due` Clock_Trigger of the Debt of criterion 2 holds, THE Narrator SHALL build a Narrator_Candidate with Salience at or above the minimum Salience and a Defensible_Option_Set.
5. THE Life_Sim SHALL add a Debt under criterion 3 only during Opening_World generation and only for the first Player_Life's body.
6. THE Life_Sim SHALL keep LS-R12.1 to LS-R12.6 and LS-R16 in force for the changed opening.
7. WHEN a World is created twice from the same seed and Params, THE Life_Sim SHALL designate the same Person as the Player_Soul's body and produce the same Debt of criterion 2 in both Worlds.
8. WHEN Opening_World generation completes, THE Life_Sim SHALL designate exactly one Debt that meets criterion 2 as the Intro_Debt and start its Intro_Grace, storing the designation and the Intro_Grace state in World state inside the Checksum and the replay.
9. WHILE the Intro_Grace holds, THE Life_Sim SHALL exclude the Intro_Debt from repayment rolls and from the `pay_debts` effect of Requirement 5.12, and SHALL apply every other Debt rule to the Intro_Debt and every Debt rule, including repayment rolls and `pay_debts`, to every other Debt unchanged.
10. WHEN the first Player_Node of the first Player_Life actually resolves, or the Intro_Debt is no longer open, or the first Player_Life ends, THE Life_Sim SHALL end the Intro_Grace in that tick, after which the Intro_Debt follows the normal Debt rules. Checking at step 4 is not itself an end condition: IF death settlement transfers the still-open Intro_Debt to an heir while the first Player_Life continues and no first node has resolved, THEN Intro_Grace SHALL continue, even if the original debtor or creditor is no longer its party.
11. THE Life_Sim SHALL hold at most one Intro_Debt per run, designated only at Opening_World generation for the first Player_Life's body, SHALL never start an Intro_Grace again after it ends, and SHALL apply no presentation-side freeze of any Debt.
12. WHILE the Intro_Grace holds, WHEN the Narrator builds an `inheritance` Narrator_Candidate, THE Narrator SHALL fix the target of its `pay_debts` option at build time to a Debt other than the Intro_Debt, offering `pay_debts` only if such a Debt exists, so that a `pay_debts` effect applied as Rules_Default or Auto_Resolved never repays the Intro_Debt (Author, 2026-11-16, decision P-1).
13. WHILE the Intro_Grace holds, THE Life_Sim SHALL let no TickInput and no step repay, forgive or close the Intro_Debt or end the Intro_Grace, other than the end conditions of criterion 10 as reached through the resolution of the first Player_Life's first Player_Node or through death settlement under the life-sim Debt rules. While the Intro_Grace holds, the only Player_Node that can be pending is that first Player_Node, so an External_Choice of `pay_debts` can be accepted only for that node, names the target fixed at its build time under criterion 12 (never the Intro_Debt), and is applied in the resolution that itself ends the Intro_Grace.
14. THE Life_Sim SHALL keep the Intro_Debt a real Debt for its whole lifetime: its `loan` Event and every later Event about it in the Event_Log, the Debt in the Checksum and the replay, and death settlement, inheritance and every closing Event applied to it under the same rules as any Debt, with only the exclusions of criteria 9 and 12 during the Intro_Grace.
15. ### Requirement 8: Clock-paced play, Worker_Protocol and pausing

**User Story:** As a player, I want the town to run at the same pace on every display and to stop exactly when something needs me, so that I never miss a choice.

#### Acceptance Criteria

1. WHILE the Run_State is `running`, THE Sim_Worker SHALL pace ticks by wall time at Speed × Play_Rate ticks per second, independent of the display refresh rate, with the pacing method set in design; this replaces WS-R4.3 and the "ticks per Frame" meaning of WS-R4.4, and keeps the Speed list 1, 7, 30, 90 and 365 with 1 selected when the page loads.
2. THE Sim_Worker SHALL produce, for one seed and one input stream, the same per-tick Checksums at every Speed, whether or not it paused under criteria 3 to 5, and whether or not it fell behind its target pace.

4. WHEN the Sim_Worker stops under criterion 3, THE Sim_Worker SHALL send the Main_Thread one `status` message, not subject to the 100 ms status throttle, carrying the tick and Checksum of that tick, every Pause_Reason of criterion 3 that applies to that tick, and the World Snapshot of Requirement 7 taken after that tick.
5. WHEN the Main_Thread sends `pause` while the Run_State is `running`, THE Sim_Worker SHALL stop under WS-R4 and SHALL report Pause_Reason `user` in its reply.
6. THE Worker_Protocol SHALL define, as types in `web/src/shared/protocol.ts`, a request for the World Snapshot, a request that submits an External_Choice naming one Node ID and one option ID, a request that submits such an External_Choice and advances one tick in the same request, requests for the dream input and the slot claim (with Carry_Over and, for the Rebuilt_Body slot only, the Customization), and a read of the pending Player_Node's answered state, and THE Sim_Worker SHALL answer each such request with exactly one reply (WS-R2.7). THE Sim_Wasm SHALL expose the answered state as a read that takes no draw, changes no state and enters no Checksum, computed from the pending Player_Node and the input stream so that it reports an accepted External_Choice from the moment the submission is accepted.
7. WHEN the Main_Thread submits a choice for the pending Player_Node, THE Sim_Worker SHALL submit it as an External_Choice TickInput for the node's Choice_Tick (the tick after the current tick, Requirement 1.5), SHALL leave the Run_State unchanged, and SHALL reply with success and the updated World Snapshot.
8. IF the Life_Sim rejects a submitted input (Requirement 1.6, Requirement 6.5 or 6.6, or an underworld rejection under LS-R1.5), THEN THE Sim_Worker SHALL reply with a failure that names the rejection, and SHALL leave the input stream, the Run_State and the pending Player_Node unchanged.
9. WHEN the Main_Thread sends `run` or `step` while a Player_Node is pending, THE Sim_Worker SHALL distinguish the two states of that node, read from the World and not from any record of what the Main_Thread has sent. IF the node has no accepted External_Choice, THE Sim_Worker SHALL refuse the request with the failure label `node_unanswered` and SHALL change nothing: no tick runs, the input stream, the Checksum history and the Run_State (`paused`) are unchanged, and the pacing anchor is unchanged. IF the node has an accepted External_Choice, THE Sim_Worker SHALL run tick t+1 and the node SHALL resolve with that choice (Requirement 1.3). A rejected submission (Requirement 8.8) is not an accepted choice and SHALL leave the node unanswered. A request that both submits a choice and asks to advance SHALL be one request handled atomically: it advances only when that choice is accepted, and on rejection it changes nothing. A repeated `run`, a repeated choice or a rejected choice SHALL cause no partial advance. This gate covers every pending Player_Node, not only the first, and it lives only in the Sim_Worker: the core keeps Requirement 1.4 and branches on no execution mode. Speed changes, `pause` and creating a new World stay available while a node is unanswered. WHEN the Main_Thread creates a new World, THE Sim_Worker SHALL cancel every scheduled frame or timer callback of the old World before posting the reply, and a callback of the old World that fires all the same SHALL neither advance the new World nor post anything, so that nothing of the old World is applied to the new World; the new World starts with no pending node. THE Sim_Worker SHALL drop no request in doing so: it handles each request to its reply before it takes the next, so no request of the old World is waiting when the new World is created, and every request, including one received before the Sim_Worker has finished loading, keeps its one reply in the order received (WS-R2.7).
10. WHEN the Sim_Cli runs a branch that answers Player_Nodes (the Playthrough_Branch, the Playthrough_Fixture recorder), THE Sim_Cli SHALL decide each answer after the firing tick t and submit it for tick t+1 before running tick t+1. Headless and replay runs are outside the Sim_Worker gate of criterion 9 and resolve an unanswered Player_Node by Requirement 1.4.
11. THE Sim_Worker SHALL keep WS-R2 and WS-R6 for the extended protocol, including the rule that no clock or random value reaches a `WasmSim` call; the wall clock SHALL set only how many ticks run per second, never a tick's input or result.

**P-1 execution scope — decided (Author, 2026-11-16):** The core keeps one default-resolution contract (Requirements 1.2, 1.4, 1.10) and branches on no execution mode; headless, CLI and replay runs use it, including for the first Player_Node. The interactive Sim_Worker is the only gate: while a pending Player_Node has no accepted External_Choice, `run` and `step` fail with `node_unanswered` and change nothing (no tick, no input, no Checksum, Run_State stays `paused`, the pacing anchor stays); once an External_Choice has been accepted, the same requests run tick t+1 and the node resolves with that choice. Accepted means recorded in the World, never "the client sent something": a rejected submission leaves the node unanswered. A request that submits a choice and asks to advance is handled atomically and advances only when that choice is accepted, and a repeated `run`, a repeated choice or a rejected choice never advances part way. The gate covers every Player_Node. The Web_App also disables the run and step controls while a node is unanswered, which is presentation and not the contract; a direct Worker request is refused the same way, and the gate's fault injection drives the Worker request path, not the disabled control. Creating a new World cancels the old World's scheduled callbacks before its reply and ignores one that fires all the same, so nothing of the old World is applied to the new World; no request is dropped, because the Sim_Worker handles one request at a time and none of the old World is waiting (ruled 2026-11-18, criterion 9). `chooser_absent` stays as a safety net reachable only from a constructed World or a headless run.

Design-phase decisions (Author, 2026-11-16, on design "Decisions for the Author"):
- **A-1 First-stop window**: new option **C**. The Intro_Debt takes no part in repayment rolls until the first Player_Life's first Player_Node has fired and resolved (Intro_Grace, Requirements 5.8 to 5.11, 13.8, 15.1). A first-life onboarding rule only: no other Debt changes, no general grace mechanism, World state inside the Checksum and replay. Target first stop about 20 to 30 s at Speed 1 (offsets about 600 to 900 ticks; 2 to 3 s rejected); `first_interrupt_min` in 600..=899, exact value in design, checked against the measured smoke time (Requirements 3.1, 16.11).
- **A-2 Fixture slot claim**: **A**. Deterministic seed search over 1..=5000 for a funeral credit that pays the dream and an Imported_Vessel, then freeze the fixture (Requirement 15.8). If no seed qualifies: no `path_executable` Pause_Reason; the Smoke_Test may use the public Step or run controls as a marked test advance method (Requirements 15.9, 16.2).
- **A-3 Rebuilt_Body Traits**: **A**. The Rebuilt_Draw is drawn once at the start of the Player_Wait and stored inside the Checksum; never redrawn at claim; Carry_Over first, then Customization overrides with an explicit UI notice; replay never redraws (Requirements 6.2, 6.3, 7.6, 11.6, 11.7, 15.1, 15.2).
- **A-4 Playthrough answers**: **A**. Largest kin affinity gain toward the body, ties to the Rules_Default; a family-minded acceptance-branch strategy, not a production AI (Requirement 13.13).
- **A-5 Feud trigger**: **B variant**. A `feud` candidate only when a Relation of the body first crosses below `grudge_threshold`; no new candidate while it stays below; eligible again only after returning to at or above the threshold (Requirements 2.11, 2.12). An escalation node is a later spec.
- **P-1 Intro_Debt protection and first-stop priority**: **A selected for `pay_debts`**. During Intro_Grace the `inheritance` `pay_debts` option targets the body's oldest other open Debt or is absent; repayment rolls also exclude only the Intro_Debt. The Intro_Debt stays real in Event_Log, Checksum, replay and death settlement. Its eligible `debt_due` candidate has first priority at its trigger tick, without changing Salience, defensibility, the band or the relative ordering of other candidates; it cannot lose to a same-tick competitor and be auto-resolved. The grace ends only on actual first-node resolution, Debt closure or first-life end; a death transfer leaving it open during an ongoing first life does not end it. The earlier reading that every step-4 death ends grace is corrected.
- **P-1 execution scope — decided (Author, 2026-11-16)**. The core keeps one default-resolution contract and never branches on an execution mode: Requirements 1.2, 1.4 and 1.10 apply to every Player_Node, including the first, and headless, CLI and replay runs (Requirements 8.10, 13.11, 15.2) use them unchanged. The interactive Sim_Worker is the only gate (Requirement 8.9): a `run` or `step` while a pending Player_Node has no accepted External_Choice fails with `node_unanswered` and changes nothing (no tick, no input, no Checksum, the Run_State stays `paused` and the pacing anchor stays); the same request after an External_Choice has been accepted runs tick t+1 and resolves the node with that choice. Accepted means recorded in the World: a rejected submission is not an accepted choice, and a request that both submits a choice and asks to advance is handled atomically, advancing only when that choice is accepted. A repeated `run`, a repeated choice or a rejected choice never causes a partial advance. The gate covers every Player_Node, not only the first. The Web_App also disables its run and step controls while a node is unanswered; that disablement is presentation, and a direct Worker request is refused the same way. The gate's fault injection drives the Worker request path (a direct `run` through the harness), not the disabled control. Speed changes and `pause` stay available. Creating a new World cancels the old World's scheduled frame or timer callbacks before its reply is posted and ignores one that fires all the same, so nothing of the old World is applied to the new World, which starts with no pending node; no request is dropped, because the Sim_Worker handles one request at a time and none of the old World is waiting (ruled 2026-11-18, Requirement 8.9). `chooser_absent` stays, reachable only from a constructed World or a headless run. The earlier proposal to block only the first node, and the option of making `sim-core` wait, are not selected.
