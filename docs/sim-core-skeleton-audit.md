# sim-core-skeleton: requirement audit (task 13)

Audited 2026-11-04 against the tree at commit `72b8abb` (plus the docs changed in this task). Every row was checked by running a command, reading the code or reading the test; "kiro-log" means the entry in `docs/kiro-log.md` for the named task, which I read but did not re-run unless the evidence column says so. No sim-core source was changed by this audit.

Status values: `met`, `met with deviation`, `not met`, `not verifiable here`, `withdrawn`.

- Artifacts (bytes): release `sim_wasm.wasm` 256,315; in `target/wasm-pkg`: `sim_wasm_bg.wasm` 232,449, `sim_wasm.js` 10,523, `sim_wasm.d.ts` 3,149, `sim_wasm_bg.wasm.d.ts` 966. The limit is 26,214,400 (25 MiB).

## Gaps and deviations

1. **R11.1-R11.4, hooks withdrawn.** What was learned: both hooks ran (`PostFileSave` only for the agent's edit-tool saves, not for shell or manual-editor saves; `PostTaskExec` on task completions), and both scripts caught injected faults when run by hand, but no hook output ever reached the agent, and the author saw no warning either (kiro-log, hook tests A and B). The requirement was withdrawn by the author on 2026-11-04, not met. The seed batch survives as a gate step; the replay check is covered by `cargo test --workspace`.
2. **R10.1.** The weekly measurement exists only as the numbers at commit `bac46e3`; the code no longer supports weekly ticks. Re-running the comparison means checking out that commit.
3. **R7.3.** The 25 MiB check is a gate script step, not a test, and it does not look at the raw release `.wasm`.
4. **R8.1 (fixed in task 15).** Thread coverage was `thread::spawn` only; now also `scope`, `Builder`, `Scope::spawn`, `available_parallelism` (see the R8.1 row). Remaining limit: names imported without a path are seen by clippy only.
5. **R8.2.** Hook injections were script-half only (the hooks are gone now); the exhaustiveness guards (Canon, `testing.rs`) had no logged injection until task 13; later gates (size check, version check, `bench` steps) had none either, except the two shown by hand in task 13. kiro-log task 7 refers to a Canon-guard demonstration "in task 5/6" that I could not find in those entries.
6. **R5.3.** Satisfied only vacuously: there is no derived state to exclude. Rule 10 (rebuild after load) is out of scope for this spec.
7. **R4.4 (corrected 2026-11-04 in the pre-push review).** An earlier version of this item said the `IdExhausted` rejection had no end-to-end test. That was wrong: `tick::tests::spawn_with_exhausted_id_counter_is_skipped_and_counted` exists and passes. It reaches the state by setting the private counter, not through the public API, which is the only way to test it without issuing 2^64 ids. Not a gap.
8. **R3.1 wording.** The requirement names three hash inputs; `draw` takes five (seed, entity, tag, tick, index) by design decision D2. Counted as met.
9. **R1.2.** The simulation's test graph contains `rand` (through `proptest`, dev-dependency only). `gates.sh` checks the `normal` tree only, which is the intended scope.
10. **Unverified log claims.** Hook marker-file observations from task 10 (temporary marker lines, later removed) cannot be re-checked. Also unexplained: the task 11 checkbox changing to `[x]` without a `task_update` call (kiro-log task 11); the second `PostTaskExec` marker line is of unknown origin.
11. **Test coverage on wasm32.** Only the sim-wasm tests run on wasm32; sim-core's unit tests, including the pinned `draw` values, run natively only.
12. **The batch gate step runs a release build** (about 5 s versus about 225 s in debug), so overflow checks and `debug_assert!` are off in that step; the rest of `gates.sh` runs tests in debug.
